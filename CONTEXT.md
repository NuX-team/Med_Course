## 1. Что это и для кого

Telegram-бот контроля курса приёма лекарств: врач составляет курс, пациент явно его начинает, бот напоминает, пациент
отвечает «принял / позже / пропустить», считается соблюдение. MVP для частных врачей в Узбекистане. Языки: русский и
узбекский (латиница). Бот не ставит диагнозы и не выбирает лечение: записывает, что сказал врач, и напоминает.

Владелец проекта (пользователь): пишет по-русски, коротко. **Не программист-ревьюер**: решения принимает по смыслу, код не
читает. Отвечать ему по-русски, без жаргона, с честным разделением «проверено / не проверено».

## 2. Как мы работаем (договорённости с владельцем)

- **Ритм:** один этап за раз. Владелец пишет «закоммить и переходи к этапу N» (или «продолжай»). Тогда: коммит
  готового этапа → реализация следующего → отчёт → вопрос «закоммитить и перейти к N+1?». **Сам не коммичу** готовый этап,
  пока не попросят: жду слова владельца.
- **Коммит:** `Stage N: <что сделано>` на английском, тело в несколько строк, в конце строка `Co-Authored-By:` с моделью
  (берётся из системного напоминания сессии). Перед каждым коммитом — проверка индекса на токен (раздел 9).
- **Docker — «потом»** (решение владельца на этапе 1). CI впервые прошёл 2026-10-04 на GitHub (снимок после этапа 13): проверки, тесты на служебном Postgres и сборка трёх
  образов — зелёные. `docker compose up --build` (запуск контейнеров) по-прежнему не выполнялся. Это долг,
  не блокер. Локально всё работает без Docker: `pnpm dev:db`.
- **Решения по умолчанию:** когда ТЗ молчит, принимаю разумное решение сам, записываю его как D-N в
  `docs/ARCHITECTURE.md` («по умолчанию, ждёт подтверждения») и упоминаю в отчёте. Не останавливаю работу вопросами.
- **Отчёт по этапу** (по-русски, коротко): что умеет, что нашла проверка, что важно знать (ограничения), что не
  проверено вживую, вопрос про следующий этап. Не преувеличивать: «проверено против поддельного Telegram» ≠ «работает».
- **Живой Telegram:** диалог в настоящем Telegram ни разу не пройден (у ассистента нет второго аккаунта). Запускал только
  собранные процессы с настоящим токеном: `getMe`, polling, `/readyz`. Каждый отчёт это повторяет.

## 3. Стек и устройство репозитория

TypeScript strict (TS 6.0.x — **не 7**: typescript-eslint его не поддерживает), Node 24, pnpm 9 workspaces, Vitest 5,

postgres.js + Drizzle ORM (только типизированные запросы), Luxon. Postgres 16. Миграции — простой SQL с up/down и

## 4. Модель и правила, которые нельзя нарушить

**Курс:** `DRAFT → PENDING_PATIENT → ACTIVE → (PAUSED) → COMPLETED`; ветви `CANCELLED`, `EXPIRED_NOT_STARTED`,
`CANCELLATION_REVIEW`, `ARCHIVED`. Каждый переход — строка в `course_transitions` (только добавление) и аудит.

**Ревизия плана:** `DRAFT → CONFIRMED → APPLIED → SUPERSEDED`. Препараты и правила расписания можно менять только в
`DRAFT`-ревизии (триггеры БД). Отправка курса делает ревизию `CONFIRMED`, старт — `APPLIED`. У идущего курса рядом с
планом в силе может быть одна ревизия «в работе» (`DRAFT` или `CONFIRMED`, уникальный индекс). `DRAFT` нельзя сделать
`SUPERSEDED` (нужен `confirmed_by_clinician_at`) — выброшенный черновик изменения **удаляется**; отправленное и
отозванное изменение становится `SUPERSEDED` без `applied_at`.

**Жизнь курса после отправки (этап 9):** врач: отзыв до старта и отмена (`CANCELLED`, причины
`WITHDRAWN_BEFORE_START` / `CANCELLED_BY_DOCTOR`), пауза, возобновление; пациент принимает изменение плана; система
завершает. `CANCELLATION_REVIEW` в MVP не используется (D-64). Возврата `PENDING_PATIENT → DRAFT` нет (D-65).

**Срез (D-62)** — одно правило для паузы, отмены и смены плана: приём с исходом не трогается; открытый с прошедшим
дедлайном → `MISSED` (момент = дедлайн); любой другой открытый, включая тот, по которому идёт напоминание, →
`SUPERSEDED`; все `QUEUED` и `SENDING` напоминания курса → `CANCELLED`. Новые слоты создаются только с
`scheduled_at > now`.

**Блокировки:** `pause/resume/cancel/completeDue/changes.*` берут строку курса `FOR UPDATE`; ответы пациента
(`answers.lockDose`) — ту же строку `FOR SHARE`, затем строку приёма. Порядок всегда «курс → приём». Не убирать
`FOR SHARE`: без него «исправить ответ» может оставить открытый приём в курсе на паузе (есть тест).

**Приём (`scheduled_doses`):** `SCHEDULED → NOTIFIED → (SNOOZED → NOTIFIED) → TAKEN | SKIPPED | MISSED`; `MISSED →
TAKEN_LATE`; `SUPERSEDED` при смене плана/паузе. `dose_events` — только добавление.

Правила доступа и безопасности:

- Репозиторий принимает `Actor` первым аргументом. «Нельзя прочитать» неотличимо от «не существует» (`null`).
  `ForbiddenError` — только когда роль в принципе не может это делать.
- Врач видит пациента только при `care_relationship = ACTIVE`, своей верификации `VERIFIED` и клинике `ACTIVE`.
- **Пациент и опекун видят курс только после того, как врач подтвердил хотя бы одну ревизию** (то есть отправил).
  Черновик пациенту невидим.
- Один черновик на пару врач–пациент (уникальный индекс `treatment_courses_one_draft_idx`).
- Курс нельзя начать, если врач потерял статус или связь закончилась (D-46); старт, после которого не осталось бы ни
  одного приёма, отклоняется (D-47). То же условие — на принятие изменения плана.
- Неотправленное изменение плана (`DRAFT`-ревизия идущего курса) пациенту невидимо: ни в `changes.get`, ни в
  `CoursePlan.change`. Изменение действует только после «Принять» пациента (D-67).
- Сообщения о паузе, отмене, смене плана и завершении уходят один раз после коммита и не повторяются (не через
  очередь `notifications`: та привязана к приёму).
- **Сообщения врачу (этап 10)** идут через очередь `doctor_alerts`: запись — в транзакции факта, текст составляется
  при отправке из того, что верно в тот момент; `decideAlert` отменяет устаревшее. Единица — **момент расписания**
  (все препараты одного времени): 1–2 подряд — отдельные сообщения, 3-й — эскалация (`SERIES`), дальше — сводка
  (`DIGEST`) не чаще раза в 6 ч и не больше одной в очереди. Принятый приём, в том числе с опозданием, обрывает серию.
  Собственные слова пациента о причине пропуска в сообщение врачу не попадают.
- **PRN:** отметка записывается всегда; сверх назначения — с `details.over` и сообщением врачу. «Сутки» — любые 24 ч.
  Отмена — событие `PRN_CANCELLED` с `details.cancels`; считать отметки только через `standingPrnMarks`.
- **Опекун** видит что-либо только при `caregiver_relationships.status = 'ACTIVE'`, а `ACTIVE` ставит только пациент.
  Опекун — отдельная роль `CAREGIVER`: все изменяющие методы репозиториев её отклоняют. Ссылка опекуна, как и
  приглашение, хранится только хэшем.
- Код приглашения не хранится нигде, только SHA-256. Свободный текст (указания к препарату, причина пропуска)
  шифруется и в аудит не попадает. Название препарата — открытым текстом (в т. ч. до 24 ч в записи диалога).
- Ответы бота — простой текст, **без `parse_mode`**: введённое человеком не может стать разметкой.
- **Панель (этап 11).** Страницы собираются только шаблоном `html` (экранирует всё; «сырого» вывода нет и добавлять
  его нельзя); клиентского JS нет, CSP `default-src 'none'`. Роли читаются из базы на каждый запрос и не хранятся в
  сессии; репозиторий перепроверяет роль сам. Техадмин не получает имён пациентов и назначений; сотрудник клиники —
  только свою клинику и без содержимого курсов. `GET /login` токен не тратит (предпросмотр ссылок), вход — `POST`.
  Каждая форма — с CSRF-токеном сессии. **Журнал запросов панели пишет путь без строки запроса** (в ней токен
  входа); стандартный журнал Fastify там выключен — не включать. Токены входа и сессий в базе только хэшем.
- `/panel` для не-сотрудника отвечает как неизвестная команда (бот не выдаёт, кто сотрудник).
- **Отправка напоминаний (этап 14).** Всегда через `Pacer` (25 в секунду на весь бот): не раскручивать выше, не
  убирать. Параллельность (`OUTBOX_CONCURRENCY`) только прячет задержку ответа Telegram; порядок «один получатель — одно
  напоминание за раунд» держит `claimDue`. Тесты, где что-то происходит «между» двумя напоминаниями, запускать с
  `concurrency: 1`. Напоминания идут раундами подряд до 20 с (`runOutboxBurst`), остальные обязанности воркера — после.
- **Оповещения (этап 14).** Текст сообщения об инциденте — только вид инцидента и «смотрите в панели»; **ничего о
  пациенте, препарате, числах**. Получатели определяются в `claimNotices`, не в воркере. `/metrics` — только числа и
  машинные коды, под токеном; не добавлять в него имена, идентификаторы и текст.
- **Админка в чате (этап 16, `telegram/admin.ts`).** Раздел показывается по `session.admin`, но **решает база**: каждый вызов идёт с
  `TECH_ADMIN`-актором и перепроверяется; `ForbiddenError` гасится в `#guarded` (молчание и сброс вопроса). Не добавлять
  в раздел ничего, что читает данные мимо репозитория, и не показывать там имена пациентов и содержимое курсов.
  Подтверждение врача — только с записью «что проверено»; список обрезается на 20 с пометкой, а не молча. Назначение
  администратора из чата — D-128 (смягчение прежнего «только командная строка»). Карточка врача —
  `clinicians.getApplication`; флаги меню — `users.menuFlags` одним запросом (не возвращать два запроса на обновление).
- **Приватность (этап 13).** `handleUpdate` сначала читает `privacy.standing`; при отозванном согласии или
  ожидающем удалении до `Flow` дело не доходит — только `PrivacyFlow.gated`. Уход пациента всегда идёт через `leave`:
  курс блокируется первым (порядок «курс → приём» сохраняется), статус `CANCELLED`, причина `PATIENT_LEFT`.
  Обезличивание трогает «замороженный» текст только через `set_config('medcourse.erasure','on',true)` и только
  обнулением; общий триггер `forbid_modification` обслуживает таблицы без поля `reason_text_enc`, поэтому условие в
  нём вложенное и через `to_jsonb` (иначе ошибка 42703 вместо отказа). У обезличенного `telegram_user_id < 0`.
  Сводки (`course_summaries`) врач читает только при `history_shared_at` у активной связи.
- **Резервные копии.** Ключ `BACKUP_KEY` не равен ни одному из `ENCRYPTION_KEYS`. Восстановление — только в пустую
  базу, суперпользователем (`session_replication_role = replica`), с последующей сверкой по манифесту.
- **Отчёт файлом (этап 12).** Получают только пациент и лечащий врач; файл уходит документом в чат нажавшего, ссылок
  нет, на сервере не хранится. Каждая выдача — строка `course_exports` + аудит `EXPORT`; лимит 10 в час на человека.
  В строки входит каждый приём с исходом (и принятый заранее): процент обязан пересчитываться по файлу. **Любая
  ячейка CSV идёт через `csvCell`** (кавычки + апостроф перед `= + - @`): названия препаратов и слова пациента —
  чужой ввод, который иначе выполнится формулой в Excel врача. Текст в PDF — только через `printable`.
- Апдейт заявляется (`tg_updates`) **до** обработки: обрабатывается не более одного раза. Напоминания — наоборот,
  «не менее одного раза» (возможен дубль, ответ идемпотентен).
- `process.env` читается только в `packages/config`. В логи и в базу от сбоев идёт только код (`HTTP_403`,
  `NETWORK`), не текст ошибки: в нём может быть адрес запроса с токеном.

Время: всё хранится в UTC; расписание считается в IANA-зоне курса (зона пациента на момент создания черновика).
Только именованные зоны, смещения вида `+05:00` отклоняются. День 1 курса — локальная дата нажатия «Начать».
Политика напоминаний по умолчанию: 3 попытки (0, +10, +20 мин), дедлайн +30 мин, «позже» 5/10/15 мин до трёх раз и не
позже чем за минуту до дедлайна, окно исправления 60 мин, отметка из «Сегодня» не раньше чем за 60 мин до приёма.

## 7. Как здесь принято проверять

1. **Тесты на настоящем Postgres**, Telegram заменён записывающей подделкой. Время всегда передаётся параметром (`now`),
   в тестах фиксированное (октябрь 2026, Ташкент = UTC+5 без перевода часов).
2. **Сквозные тесты бота** через `createHarness`: `bot.say(id, текст)`, `bot.press(id, данные, messageId?)`,
   `bot.clock = …`; смотреть `telegram.lastTo(id)`, `telegram.messagesTo(id)`.
3. **Мутационная проверка в конце каждого этапа:** скрипт на Python по очереди ломает одно правило в коде (замена
   строки), гоняет нужные тесты, возвращает файл. Все мутации должны быть пойманы. Выжившая мутация = пробел в тестах
   (так на этапе 7 нашлось, что тест «20 одновременных нажатий» ничего не доказывал). Скрипты лежат в scratchpad сессии
   и не коммитятся; образец логики — в разделе 8.
4. **Гонки проверять детерминированно:** отдельное соединение держит `FOR UPDATE` на строке, тест ждёт, пока все участники
   появятся в `pg_stat_activity` с `wait_event_type = 'Lock'`, и отпускает разом. Готовые помощники:
   `holdLock`, `waitForBlocked` из `@medcourse/db/testing` (примеры — `lifecycle.db.test.ts`, `changes.db.test.ts`).
   Чтобы задать порядок участников, запускать их по одному и ждать `waitForBlocked(1)`, `(2)`… Простое `Promise.all`
   из N вызовов гонку **не гарантирует**.
5. **Живой запуск** собранных процессов на локальной базе: миграция применяется, `/readyz` отвечает, в логах нет
   токена и строк уровня error/fatal.
6. После этапа обновить `PROJECT_STATUS.md`, `docs/ARCHITECTURE.md`, `README.md` и этот файл.

## 8. Грабли среды (Windows, инструменты)

- **Bash + heredoc с кавычками/бэктиками ломается** («unexpected EOF»). Надёжно: файлы создавать инструментом Write;
  правки — Edit или Python-скрипт, записанный в scratchpad через `cat > файл <<'PY' … PY` и запущенный отдельно.
  `node -e "…"` с шаблонными строками внутри — не использовать.
- **Python на Windows:** читать/писать только `io.open(path, encoding='utf-8', newline='')`, иначе появятся CRLF и
  cp1251. Запускать с `PYTHONIOENCODING=utf-8`. После правок скриптом — `prettier --write`.
- **`pnpm exec vitest` из скрипта возвращает код 0 даже при упавших тестах.** Судить по выводу: строки с `×` и итог
  `Tests … failed`.
- **PowerShell:** `@($x -match …).Count` на одной строке даёт ложную единицу — фильтровать через `Where-Object`.
  `&&` нет. Инструмент блокирует команды, похожие на удаление системных путей (не вставлять `Remove-Item` рядом с
  регулярками).
- **Фоновые процессы** (`pnpm dev:db`, `dev:bot`): запускать через Bash с `run_in_background`, останавливать через
  `Get-CimInstance Win32_Process` по имени `node.exe`/`postgres.exe` и `CommandLine -match 'MedCourse'` + `Stop-Process`.
  Уведомление «failed with exit code 127» после этого — норма.
- **Порт может быть занят чужим процессом** (так было с 3055): для разовых запусков брать 3977–3979.
- **Postgres на русской Windows** создаёт базу в WIN1251: тестовый и dev-кластеры создаются с `--encoding=UTF8
--locale=C`, раннер миграций отказывается работать не с UTF-8.
- **Drizzle меняет сериализаторы клиента postgres.js**, поэтому клиентов два: `db.sql` (сырой) и `db.orm`. В сыром
  `sql\`…${date}\``на orm-клиенте`Date` не привязывается — использовать операторы Drizzle (`lte`, `gte`).
- **`created_at default now()`** в одной транзакции одинаков для всех строк: порядок задавать явно.
- **`process.exit()` обрывает вывод в пайп на Windows** — в CLI использовать `process.exitCode`.
- Тесты, которым нужна «чистая» очередь напоминаний, в `beforeEach` переводят чужие `QUEUED/SENDING` в `CANCELLED`
  (и обязательно `locked_until = null`, иначе `notifications_lock_chk`).
- `sweepMissed` и `completeDue` работают по всей базе тестового файла и пачками по 200: в тестах вызывать в цикле «пока
  не вернёт 0» и фильтровать результат по своему курсу.
- Одному получателю — одно напоминание за раунд: чтобы дошло третье по очереди, нужно три вызова `runOutbox`.
- Мутационный скрипт на время прогона меняет исходники: пока он работает в фоне, не править код и не запускать тесты.
- В Python-скрипте, записанном через Write, `\\n` внутри строки даёт в TS `\n`; через heredoc — настоящий перенос.
- **Не называть файлы `prn`, `con`, `aux`, `nul`, `com1`, `lpt1`** (с любым расширением): на Windows это имена
  устройств. Файл `prn.ts` создаётся и даже компилируется, но `git add` его открыть не может. Поэтому приём «по
  необходимости» живёт в `as-needed.ts`.
- `pnpm check > файл; echo $?` печатает 0 и при упавших тестах: судить только по строкам `Tests`/`×` в выводе.
- **Prettier переформатирует шаблоны `html\`…\``** (переносы и отступы внутри разметки): в тестах сравнивать HTML по
подстрокам или после `.replace(/>\s+</g, '><')`, а в мутационном скрипте брать строки уже после форматирования.
- Гонку «роль отозвали между чтением сессии и чтением данных» тест воспроизводит обёрткой `Proxy` над `orm`,
  которая перед `transaction` делает отзыв (`app.db.test.ts`). Оборачивать только `transaction`: остальные методы
  Drizzle возвращают построитель запроса синхронно.
- `reply.send()` в Fastify возвращает thenable: `await` на нём в охраннике не нужен, а `return reply` после уже
  отправленного ответа — правильный способ закончить async-обработчик.
- `font.generated.ts` (2 МБ) исключён из Prettier (`.prettierignore`) и ESLint (`**/*.generated.ts`); не открывать
  его целиком и не форматировать.
- PDF можно посмотреть инструментом Read (без параметра `pages`: для него нужен `pdftoppm`, которого нет).
- `sed -i` с кавычками и скобками молча ничего не меняет — проверять `grep` или править Edit'ом.
- `hygiene.test.ts` читает `git ls-files --cached --others --exclude-standard`: новый файл попадает под проверку до
  коммита. Он падает, если в файле токеноподобная строка: тестовые фальшивые токены допускаются только из списка
  `MADE_UP` в самом тесте. Шаблон токена нельзя писать с `\b`: настоящий токен может кончаться на `-`.
- Счётчик «все 3 строки» от `grep -c "$X"` при пустом `$X`: каждый вызов Bash — новая оболочка, переменные не
  переживают вызов; проверку «токена нет в журнале» делать в одной команде с запуском процесса.
- В этой среде нет `pg_dump`/`psql` (в embedded-postgres только сервер): всё, что нужно от базы, делать через
  postgres.js. Для команд копий ключ передавать в окружении: `BACKUP_KEY=devdrill:<base64> pnpm db:backup …`.
- Правку применённой миграции делать так: сначала `pnpm db:rollback` на dev-базе, потом менять файл, потом
  `pnpm db:migrate` (иначе раннер упрётся в контрольную сумму).
- `consent_records.at` и `audit_log.at` ставит база (`now()`), а не часы теста: сортировка «последнее по времени»
  в тестах с часами из прошлого идёт по реальному времени. Не передавать туда тестовое `now`.
- В PL/pgSQL обращение `new.<поле>` падает (42703), если у таблицы такого поля нет, даже за `and`: в общих
  триггерных функциях проверять через `to_jsonb(new) ->> 'поле'` и вложенный `if`.
- Чтобы проверить, что код работает из однофайловой сборки, временно положить точку входа и `tsup.tmp.config.ts`
  в `apps/bot`, собрать `tsup --config …`, запустить и удалить.
- Скрипт, которому нужны пакеты репозитория (`@medcourse/db/testing`), из scratchpad их не найдёт: на время запуска
  класть его в `apps/panel/` и удалять после.

## 9. Секреты и происшествие с токеном

- Токен бота лежит **только** в `.env` (в `.gitignore`). В `.env.example` строка `TELEGRAM_BOT_TOKEN=` пустая.
- **Никогда не печатать значение токена** и не просить его в чат; перечислять только имена переменных.
- **Происшествие:** владелец положил настоящий токен в `.env.example`, и он попал в коммит этапа 3 (`3119cf0`). Из файла
  убран (коммит этапа 4), перенесён в `.env`. **В истории git остаётся.** `git commit --amend` заблокирован защитой
  среды — в обход не делать. Наружу не уходил: на GitHub отправляется только снимок без истории. Владельцу рекомендовано отозвать токен у @BotFather
  (`/revoke`); сделал ли — неизвестно, напоминать в отчётах.
- **GitHub.** Основной репозиторий с 2026-10-09 — приватный `NuX-team/Med_Course` (организация владельца), remote
  называется `nux` (не `origin`). Два прежних — личные `phant0mcyber01-hud/Med_Course` (remote `med-course`, снимок
  `47ff583`) и `phant0mcyber01-hud/medcourse` (remote `github`, снимок `44d7df4`) — остались как есть: туда больше не
  отправлять и их не удалять без слова владельца. Репозиторий организации видят её участники: секретов в снимке
  быть не должно тем более. Уходит **снимок без истории**:
  локальная ветка `github-snapshot`, где каждый коммит — дерево `main` на конец этапа, а предок — предыдущий снимок.
  Локальную `main` на GitHub **не отправлять никогда**: в её истории действующий токен (так выбрал владелец, пока
  токен не отозван). Обновление снимка после коммита этапа:
  `git commit-tree "main^{tree}" -p github-snapshot -m "Stage N: …"` → `git branch -f github-snapshot <sha>` →
  проверить снимок на токен (`git grep` по `<sha>`) → `git push nux github-snapshot:main`. Отправлять только по
  слову владельца. Когда владелец отзовёт токен, можно предложить залить полную историю отдельной веткой.
- **Перед каждым коммитом:** `git add -A && git grep --cached -l "<начало токена>"` должно быть пусто (начало токена
  смотреть в `.env`, в файлы не выписывать). В тесте конфига есть выдуманный токен — это нормально.
- Тестовые ключи шифрования с id `dev…` разрешены только при `APP_ENV=local`.

## 11. Известные долги и дыры (честный список)

- Диалог в живом Telegram не пройден ни разу; ни одно настоящее напоминание не отправлялось.
- `docker compose up` (запуск собранных контейнеров вместе с базой) не выполнялся. CI и сборка трёх образов на GitHub
  прошли один раз, на снимке после этапа 13; CI идёт только при отправке снимка на GitHub.
- Токен в истории git (раздел 9).
- Тексты согласия не проверены юристом; узбекские переводы не проверены носителем языка.
- У врача нет настроек уведомлений и тихих часов: сообщение о пропуске придёт и ночью.
- Клиника — только «частная практика» одного врача: создать клинику из нескольких врачей или перевести врача нельзя,
  так что ресепшн в панели — помощник одного врача. `CLINIC_ADMIN` и `RECEPTION` в панели равны.
- При неработающем воркере технический инцидент открыть некому (о беде тогда скажет только внешний мониторинг
  `/metrics`, которого ещё нет). В панели нет выхода «на всех устройствах». Оповещения об инцидентах — только в Telegram:
  если он недоступен, остаётся панель.
- Панель отвечает 404 на `/favicon.ico` (браузер просит его сам): лишняя строка в журнале на страницу, вреда нет.
- `/panel` при `PANEL_BASE_URL = null` всё равно создаёт строку `panel_logins` (ссылка не отправляется, строку уберёт
  уборка): мелочь, но расходует лимит ссылок.
- Опекун не получает сообщений о пропусках (только смотрит сам); отключить опекуна может только пациент.
- Незарегистрированный человек по ссылке опекуна сначала регистрируется и открывает ссылку заново (ссылка через
  регистрацию не «проносится», в отличие от приглашения пациента).
- Сообщения о паузе, отмене, смене плана и завершении не повторяются при сбое Telegram, и врач не узнаёт о недоставке.
- Курс на паузе может стоять вечно; пациент не может явно отклонить изменение плана (только не принять), и врач об этом
  не узнаёт; у предложения нет срока.
- Длительность идущего курса изменить нельзя (D-66); изменить дозу = убрать препарат и добавить заново (новая `line_id`).
- `completeDue` берёт 200 кандидатов по дате старта: если накопится 200+ курсов, которые нельзя закрыть (открытые
  приёмы), более новые будут ждать. При объёмах пилота не достижимо; при росте — добавить курсор.
- После правила среза приём, по которому шло напоминание в момент смены плана, пропадает из учёта, даже если препарат
  в новом плане тот же (D-62, осознанный выбор в пользу безопасности).
- Резервная копия по расписанию — контейнер `backup` в `deploy/docker-compose.prod.yml` (на часах сервера не
  запускался); на другой носитель её никто не выносит: диск сервера один на базу и копии, это дело владельца. Восстановление из старой копии возвращает уже удалённые данные (повторять обезличивание
  по журналу воркера вручную). Копия большой базы не делалась.
- Сроки хранения медицинских записей не заданы: по сроку ничего не удаляется. Удаление аккаунта врача или
  сотрудника — только вручную. Сообщение врачу «пациент отключился» одноразовое, без очереди.
- Отчёт файлом: только по одному курсу; журнал аудита файлом не выгружается (ТЗ §14.2); файл собирается синхронно
  при нажатии; CSV не открывался в настоящем Excel, PDF — в Adobe Reader и на телефоне; бандл бота 8 МБ из-за шрифта.
- Мастер курса делает только простую схему: каждый день в заданные часы или PRN; единица «другое» не предлагается.
- Название препарата всегда видно в напоминании (настройка скрытия, D-4, не сделана).
- QR-код приглашения отложен (D-30).
- Курс, не начатый в срок, виден пациенту только в «Истории» (одной строкой, без кнопки).
