## 1. Кратко

Telegram-бот, в котором врач оформляет курс приёма лекарств, а пациент явно нажимает «▶️ Начать курс»,
получает напоминания по подтверждённому врачом расписанию и отмечает «Принял / Позже / Пропустить».
Врач видит соблюдение расписания (adherence). MVP — проверка спроса у частных врачей в Узбекистане.

Сервис организует назначенное врачом лечение. Он не ставит диагнозы, не выбирает препараты и дозы,
не меняет схему и не советует менять её самостоятельно.

## 2. Архитектура (план)

Три процесса поверх общего ядра и одной PostgreSQL: `apps/bot` (webhook), `apps/worker` (outbox, sweeper'ы),
`apps/panel` (панель для сотрудников). Очередь — таблица `notification` как transactional outbox, Redis не нужен.
Подробности — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Ключевые инварианты, на которых держится всё остальное:

- Напоминаний до явного старта курса пациентом нет.
- Старт — один атомарный `UPDATE … WHERE status='PENDING_PATIENT'`; повтор — no-op.
- Приёмы материализуются при старте; события append-only; изменение плана = новая ревизия.
- Любой job перед отправкой сверяет статус курса, приёма и ревизию.
- Доступ врача к пациенту — только через активную `care_relationship`; проверка в серверном слое.

### Этап 2 — схема БД, права, аудит ✅

- **Миграции** — 4 пары `.up.sql`/`.down.sql`, свой раннер (transaction на миграцию, advisory lock, контрольные суммы,
  CLI `db:migrate` / `db:rollback` / `db:status`, в production откат запрещён). Проверено: вверх → вниз до пустой схемы →
  вверх даёт идентичную схему; две одновременные миграции применяют каждую ровно один раз; упавшая миграция откатывается целиком.
- **Схема:** 17 таблиц; всё, что можно, закреплено ограничениями БД (составные внешние ключи против «чужих» связей,
  неизменяемость подтверждённого плана, PRN без расписания, согласованность состояния курса и приёма, журналы только на
  дописывание). Список — [ARCHITECTURE §4.4](docs/ARCHITECTURE.md); каждое правило покрыто тестом.
- **Drizzle** описывает таблицы для запросов; `schema.db.test.ts` падает при расхождении колонок, типов, nullability, индексов
  и значений enum с SQL.
- **Слой доступа:** `Actor` (роль-ёмкость), SQL-предикаты видимости, репозитории пациентов, курсов, приёмов и событий.
  Права, которые можно отозвать, проверяются при каждом запросе.
- **Аудит:** запись в транзакции операции; только имена полей и HMAC-хэши, текста нет; чтение ПДн не пациентом пишется в аудит.
- **Шифрование полей:** AES-256-GCM, ключ-кольцо `ENCRYPTION_KEYS`, привязка шифртекста к `таблица.колонка:id`.
- **Проверено на настоящем Postgres 16** (встроенный, без Docker): 209 тестов БД. Матрица доступа: пациент, врач, коллега,
  врач другой клиники, ресепшн, техадмин, опекуны (активный / с причинами / ожидающий), система; отзыв прав (связь, верификация,
  клиника, блокировка, опекун, персонал) действует мгновенно. IDOR-тесты ловят намеренно внесённые дефекты предикатов
  (3 мутации: 4, 2 и 11 падений).

**Найдено и исправлено по ходу:**

- `drizzle()` подменяет сериализаторы времени и JSON на переданном ему клиенте postgres.js, из-за чего `Date` в обычных
  запросах не биндился. Теперь Drizzle получает отдельный клиент (регрессионный тест).
- `create table if not exists schema_migrations` не защищён от гонки двух мигратор: создание таблицы теперь под advisory lock.
- Предикат административного списка игнорировал клинику, в роли которой действует актор: сотрудник двух клиник видел бы
  обе. Теперь актор «клиника A» видит только клинику A.

**Не входит в этап (по плану):** уникальность терминальных событий «среди неисправленных» (этап 8), PRN-события через
репозиторий (этап 10), мутации курса кроме открытия черновика (этапы 6–9), отзыв прав у роли приложения в БД (этап 14),
доставка миграций вместе с деплоем (этапы 14–15).

### Этап 3 — ядро расписания (`packages/schedule`) ✅

Чистые функции: без БД, Telegram и текущего времени (всё, что зависит от «сейчас», получает его аргументом).

- **День курса и пауза** (`CourseTimeline`, `courseDayAt`): день 1 — локальная дата нажатия в зоне пациента; день,
  целиком лежащий внутри паузы, не считается (курс удлиняется), частично покрытый — считается; открытая пауза оставляет
  конец неизвестным.
- **Генерация слотов** (`generateSlots`): детерминированная, с правилами по дням недели и диапазонам дней; слот ≤ момента
  старта не создаётся (D-8); защита от дубликатов и лимит.
- **Валидация плана** (`validatePlan`): все проблемы разом, коды для локализации.
- **Напоминания** (`ReminderPolicy`): дедлайн, времена попыток, предварительное напоминание, варианты «позже», окно исправления.
- **Тайминг ответа** (`classifyAnswer`), **старт** (`startWindowState`, `previewStart` для двухшагового подтверждения),
  **смена плана и пауза** (`planRevisionSwitch`, `planPause`), **adherence** (`summarizeAdherence`, формула печатается
  константой), **тихие часы** (`isInQuietHours`).
- **Время:** только именованные зоны IANA (смещение `+05:00` отклоняется), правила для «несуществующего» и «повторяющегося»
  часа при переходе на летнее время зафиксированы и протестированы на Europe/Berlin. Подробности — [ARCHITECTURE §5.5–5.6](docs/ARCHITECTURE.md).
- **Проверено:** 199 юнит-тестов, в том числе 300 случайных планов против независимого оракула на чистой арифметике UTC
  (Ташкент не знает перехода), 60 случайных пауз против проверки «минута за минутой» в двух зонах, граничные случаи по
  миллисекундам. Контракт с БД (26 тестов на Postgres): списки статусов совпадают; значения по умолчанию политики равны
  колонкам; валидатор политики согласен с CHECK-ограничениями на 400+ комбинациях; валидатор плана не мягче базы там, где
  база что-то проверяет; сгенерированное расписание ложится в `scheduled_doses` без нарушений, замена плана работает.
  Девять намеренных дефектов в граничных условиях ловятся тестами (2–10 падений каждый).

**Найдено и исправлено по ходу:**

- Среда принимает смещение `+05:00` как «часовой пояс»; теперь отклоняется (архитектура запрещает фиксированные смещения).
- Luxon сохраняет имя зоны как передано; канонизация регистра теперь идёт через `Intl`.
- При некорректной длительности курса валидатор дополнительно ругался на каждый препарат; теперь только на причину.

**Не входит в этап:** автоматы состояний курса и приёма (`core`, этапы 7–9; здесь только чистая арифметика времени),
хранение интервалов паузы (этап 9), идентификатор-карточки уведомлений (этап 8).

### Этап 4 — Telegram-адаптер, онбординг пациента ✅

Всё проверено автоматически; **с живым Telegram не проверялось** (в проекте нет `.env` с токеном): обмен с Telegram
заменён записывающей подделкой, остальное настоящее (обработчик, репозитории, Postgres). Как проверить вживую — раздел 7.

- **Приём апдейтов:** webhook (секрет проверяется до разбора тела, путь выводится из секрета) и polling для локальной
  работы без публичного адреса. Ограничитель частоты, дедупликация по `update_id` (claim до обработки: не более одного раза),
  работа с БД в одной транзакции, ответы в Telegram после коммита. Сбой обработки → извинение, 200 в webhook.
- **Онбординг:** язык → согласие (версия текста записывается) → имя → фамилия → часовой пояс → меню. Аккаунт создаётся
  в момент согласия; отказ не оставляет ничего. Состояние шагов в БД (`conversation_states`, 24 ч), не в памяти.
  Меню, «Мой курс/Сегодня/История» («курсов нет»), настройки (язык, часовой пояс), `/help` с аварийной оговоркой.
- **Локализация** (`packages/i18n`): RU и UZ (латиница); узбекский типизирован по русским ключам; тесты на совпадение
  подстановок, длины, оговорки. **Тексты согласия — на юридическую проверку, узбекский — на проверку носителем.**
- **Миграция 0005:** `tg_updates`, `conversation_states`, `consent_records` (append-only), `users.timezone_confirmed_at`.
- **Воркер:** уборка старых `update_id` (>7 суток) и просроченных диалогов раз в час.
- **Инструменты:** `pnpm dev:db` — локальный Postgres 16 без Docker (данные в `.dev-pg/`, параметры как в `.env.example`).
- **Проверено:** 133 теста бота (из них 39 сквозных на Postgres: полный путь на двух языках, отказ от согласия,
  повторная доставка, двойные и одновременные нажатия, устаревшие кнопки, чужие чаты, заблокированный пользователь,
  истечение диалога, сбои БД и Telegram), 26 на i18n, 14 на конфиг Telegram. Девять намеренных дефектов (секрет не
  проверяется, повтор обрабатывается дважды, согласие не пишется, устаревшая кнопка действует, группы отвечаются,
  заблокированные обслуживаются, зона берётся из кнопки, поиск находит прототип, символ смены направления в имени)
  ловятся тестами. Собранный бандл бота запущен: стартует, отвечает на `/healthz`, получил от Telegram 401 на вымышленный
  токен и продолжил работать, токена в логах нет.

**Найдено и исправлено по ходу:**

- `decodeCallback('m:__proto__')` возвращал функцию вместо цели меню (поиск в обычном объекте): найдено фаззингом.
- Postgres, созданный на русской Windows, имеет кодировку WIN1251 и не сохраняет эмодзи в имени. Тестовый сервер теперь
  UTF-8, а раннер миграций отказывается работать с базой не в UTF-8.
- Символ U+202E (смена направления текста) проходил как имя и мог выдать одно имя за другое перед врачом. Теперь отклоняется.
- Webhook разбирал тело до проверки секрета; теперь проверка раньше.
- Неизвестная команда зарегистрированному пользователю отвечала «понимаю только текст»; теперь показывается меню.

**Не входит в этап:** приглашения и привязка к врачу (этап 5; ссылка `/start i_<код>` пока игнорируется, D-24),
просмотр и отзыв согласия, запрос удаления (этап 13), поздние сообщения «бот заблокирован пользователем».

### Этап 5 — врач и подключение пациента ✅

Проверено автоматически; **диалог в живом Telegram не пройден** (бот с настоящим токеном запускался: `getMe`, polling и
`/readyz` работают, токена в логах нет, но никто не писал боту). Как пройти вручную — раздел 7.

- **Заявка врача:** кнопка «Для врачей» в меню (или `/doctor`) → короткое объяснение → одно сообщение «где работаете,
  специальность, лицензия» (до 500 символов, видит только проверяющий) → профиль `PENDING` и частная практика (клиника из
  одного врача, D-26). Имя берётся из регистрации. До проверки врач не может ничего: ни приглашать, ни видеть пациентов.
- **Проверка врача:** `pnpm admin` (раздел 7): `grant-admin`, `list-doctors`, `verify-doctor`, `revoke-doctor`. Проверять
  может только активный `TECH_ADMIN`, и это проверяется в базе при каждом вызове. Отзыв действует мгновенно: врач теряет и
  пациентов, и возможность приглашать. После проверки бот пишет врачу на его языке.
- **Приглашение:** врач → «Пригласить пациента» → пометка «как зовут» (для себя; можно пропустить) → ссылка
  `https://t.me/<бот>?start=i_<код>`. Код — 16 случайных байт (22 символа), **в базе только SHA-256**; одноразовый, 72 часа,
  не больше 20 неиспользованных у врача. Список приглашений с оставшимся временем и отзывом.
- **Пациент по ссылке:** новый человек сначала проходит регистрацию (в разговоре хранится только хэш ссылки), потом видит
  «Врач … приглашает вас» и решает; зарегистрированный видит предложение сразу. «Подключиться» создаёт связь `PENDING` с
  отметкой согласия пациента и пишет врачу с кнопками «тот человек / другой». Подтверждение → `ACTIVE`, пациент получает
  сообщение; отказ → `ENDED`, пациенту нейтральный текст (D-28). До подтверждения врач видит **только имя** ожидающего.

### Этап 6 — мастер создания курса ✅

- **Черновик:** карточка всего назначения, «Добавить», «Убрать», «Изменить длительность» (препараты «на весь курс»

- **Доступ:** пациент (и опекун) видит курс только после того, как врач подтвердил хотя бы одну ревизию, то есть отправил

### Этап 7 — старт курса и материализация ✅

Проверено автоматически; **в живом Telegram не пройдено**. Собранные бот и воркер запускаются, миграция 0008 применяется на
локальной базе. **После старта напоминания не приходят:** они создаются в очереди (`notifications`), а отправлять их начнёт
воркер на этапе 8. Текст «я буду присылать напоминания» станет правдой только тогда.

- **Кнопка «▶️ Начать курс»** под назначением, которое пришло от врача, и в «Мой курс». Если ждут несколько курсов, они
  пронумерованы, и кнопка называет свой.
- **Два нажатия (D-7).** Первое ничего не меняет и показывает, что будет, если начать сейчас: «сегодня день 1 из N,
  последний день такой-то», сколько приёмов осталось сегодня и во сколько первое напоминание. Если часть сегодняшних
  приёмов уже прошла, это сказано прямо («осталось 1 из 2, прошедшие не переносятся и не считаются пропущенными»).
  Второе нажатие начинает курс.
- **Старт один раз.** Одна транзакция: условный `UPDATE … WHERE status = 'PENDING_PATIENT'` и в окне старта, ревизия
  становится `APPLIED`, создаются приёмы (`scheduled_doses`) и напоминания к ним, пишутся переход и аудит. Из любого числа
  одновременных нажатий курс начинает ровно одно, остальные получают «уже начат»; позднее нажатие дату не сдвигает.
- **Что создаётся.** Только приёмы строго после момента нажатия (D-8), в часовом поясе курса; день 1 считается по
  календарю пациента, а не сервера. На каждый приём по настройкам курса (по умолчанию 3 напоминания: в срок, +10, +20
  минут; дедлайн +30 минут), при включённом предупреждении — ещё одно заранее, но не в прошлом.
- **Когда начать нельзя:** срок истёк (с датой и именем врача, D-5); врач потерял статус, практика приостановлена или
  связь закончилась (D-46); если начать сейчас, в курсе не останется ни одного приёма (D-47); курс чужой или ещё
  черновик. Во всех случаях ничего не создаётся.
- **Врач** получает сообщение «пациент начал курс» на своём языке, один раз.
- **«Мой курс»** у пациента: идущий курс с датой начала, последним днём и «сегодня день X из N». **«Сегодня»:** приёмы
  сегодняшнего дня по времени с препаратом, дозой и состоянием (по календарю пациента).
- **Воркер** раз в пять минут закрывает курсы, которые не начали в срок (`EXPIRED_NOT_STARTED`); само окно проверяется в
  момент нажатия, так что задержка воркера ничего не разрешает.
- **Миграция 0008:** таблица `notifications` (очередь: приём, вид, номер попытки, срок, состояние), один ряд на
  приём/вид/попытку.
- **Проверено:** 35 тестов репозитория старта (включая независимо посчитанные моменты приёмов, границы окна и момента
  нажатия, другой часовой пояс, курс на 840 приёмов), 28 сквозных на Postgres с поддельным Telegram, тесты воркера,
  кодек. Двадцать намеренных поломок ловятся тестами.

**Найдено и исправлено по ходу:**

- **Тест «20 одновременных нажатий» не проверял то, что обещал.** Мутационная проверка показала: если убрать из
  `UPDATE` условие на статус, тест всё равно проходил, потому что при прогретом пуле соединений нажатия не пересекались.
  Добавлен детерминированный тест: строка курса удерживается блокировкой, пока все нажатия не дойдут до `UPDATE`, и
  отпускается разом. Теперь снятие условия ловится.
- Похожие тесты «одновременных нажатий» в этапах 5–6 (приглашения, отправка курса, ответ врача) написаны по старому
  образцу. Их защита (`FOR UPDATE`, уникальные индексы) проверена и другими тестами, но как детекторы гонок они слабее,
  чем выглядят. Перевести их на тот же приём — долг (не блокирует этап 8).

**Не входит в этап:** отправка напоминаний и ответы «принял / позже / пропустить» (этап 8), пауза, отмена, правка и
отзыв курса (этап 9), история и процент соблюдения (этап 10). Курс, не начатый в срок, исчезает из «Мой курс» (старая
кнопка объясняет почему); показывать его в истории — этап 10.

### Этап 8 — worker, напоминания и ответы ✅

Проверено автоматически, включая сквозной сценарий «слот → напоминание → ответ», где настоящий код воркера и бота работают
на одной базе через один поддельный Telegram. **В живом Telegram напоминания не отправлялись**: собранный воркер запускался
с настоящим токеном при пустой очереди. Пройти вживую — раздел 7.

- **Отправка (воркер).** Раз в две секунды берёт из очереди то, что пора (`FOR UPDATE SKIP LOCKED`), резервирует на минуту
  и перед самой отправкой проверяет заново: курс идёт, приём ещё ждёт ответа, план не заменён, аккаунт открыт, дедлайн не
  прошёл. Что уже неправда, отменяется без сообщения. Одному человеку — одно сообщение за раунд.
- **Напоминание:** «Пора принять лекарство», препарат, доза, еда, время по часам пациента, указание врача, «отметить
  вовремя можно до…». Со второго раза — «напоминаю ещё раз». Кнопки: «Принял», «Через 5/10/15 мин» (только те, что ещё
  успевают до дедлайна), «Пропустить».
- **«Принял»:** до дедлайна — принят; после — **пропуск остаётся, к нему добавляется «принят с опозданием»** (ТЗ §7.7).
  Раньше чем за час до приёма — отказ как случайное нажатие.
- **«Позже»:** напоминание возвращается в выбранную минуту; запланированное время приёма не двигается. Не больше трёх раз,
  и вариант, который пришёл бы после дедлайна, отклоняется, а не укорачивается молча.
- **«Пропустить»:** причина «Забыл / Нет лекарства / Другая»; для «другой» можно написать свой текст (до 300 символов,
  шифруется, с предупреждением не писать срочное) или нажать «Без комментария». После дедлайна пропустить нельзя: это уже
  пропуск.
- **«Исправить ответ»:** в течение часа пациент может отозвать свой ответ; приём возвращается в ожидание (оставшиеся
  напоминания восстанавливаются) или в пропуск, если дедлайн прошёл. В журнале остаются оба события и запись об исправлении.
- **Пропуск по дедлайну:** воркер раз в 30 секунд переводит неотвеченные приёмы в «пропущен» с моментом самого дедлайна,
  а не момента проверки.
- **Сбои Telegram:** лимит (429) — ждём, сколько сказано; сеть и 5xx — повтор с растущей паузой до минуты; бот заблокирован
  или чат не найден (403, 400) — окончательный отказ без повторов. Повтор, который пришёл бы после дедлайна, не делается.
  В базу и в логи попадает только код ошибки.
- **Падение воркера:** до отправки — напоминание уйдёт позже (резерв истекает через минуту); после отправки, но до
  записи — пациент может получить напоминание дважды, и один ответ закрывает оба. Ни потери, ни двойной записи приёма.
- **«Сегодня»** стало способом ответить без напоминания: приём открывается кнопкой с часа до его времени; пропущенный
  можно отметить «всё же принял».
- **Общий пакет `packages/telegram`:** кнопки, текст напоминания и вид дозы теперь одни на бот и воркер.
- **Миграция 0009:** счётчик попыток и код последней ошибки у напоминания, вид диалога `DOSE`.
- **Проверено:** 33 теста ответов и 18 очереди (репозитории), 39 воркера, 24 сквозных, текст напоминания и кодек.
  Двадцать восемь намеренных поломок ловятся тестами.

**Найдено и исправлено по ходу:**

- Мутационная проверка показала пробел в тестах: ничто не проверяло, что текст, набранный там, где ждут кнопку, не
  сбрасывает незаконченный шаг мастера. Тест добавлен; сам код вёл себя правильно.
- Воркеру для отправки нужен только токен, а проверка конфигурации требовала от него настроек вебхука. Теперь процесс,
  который только отправляет, загружает токен без них.

**Не входит в этап (и это важно знать):**

- **Врач не узнаёт о пропусках и о том, что сообщение не доставлено** (бот заблокирован): уведомления врачу — этап 10.
  Недоставленное напоминание сейчас видно только в базе (`notifications.status = 'FAILED'`).
- Отметка приёма «по необходимости» (PRN), история и процент (этап 10).
- Старые сообщения-напоминания не редактируются воркером: кнопки на них остаются и при нажатии показывают текущее
  состояние приёма.
- Настройка «скрывать название препарата на экране блокировки» (D-4) не сделана: название в напоминании видно всегда.
- Ежедневная сверка очереди и приёмов (архитектура §8) не сделана.

### Этап 9 — пауза, ревизии, отмена, завершение ✅

Проверено автоматически: репозитории на настоящем Postgres, сквозные сценарии бота и воркера через поддельный Telegram,
гонки — детерминированно. **В живом Telegram не пройдено ничего из этого этапа.**

- **Отзыв до старта.** Курс, который пациент ещё не начал, врач может отозвать (два нажатия: вопрос, потом «да»).
  Пациент получает сообщение, начать курс уже нельзя (старая кнопка объясняет почему). Исправить назначение — значит
  отозвать и создать новый курс: бот сразу предлагает взять отозванный за основу (D-65).
- **Пауза.** С момента паузы пациенту ничего не напоминается: все приёмы без ответа снимаются с расписания (в том числе
  тот, по которому напоминание уже идёт) и не считаются пропусками; приём, срок которого вышел до паузы, записывается
  пропуском с моментом своего дедлайна. Напоминания отменяются, включая уже взятые воркером из очереди. На паузе пациент
  не может отвечать по старым кнопкам и исправлять ответы.
- **Возобновление.** План раскладывается заново строго после момента возобновления. День, целиком простоявший на паузе,
  не входит в длительность: конец курса сдвигается, врач и пациент получают новую дату. Приёмы, выпавшие на паузу, не
  восполняются (D-20). Дни препарата («дни 1–3») тоже считаются по дням лечения.
- **Отмена идущего курса.** Сразу и окончательно: напоминания прекращаются в тот же момент (D-11), всё записанное
  остаётся. Для частной практики отмена не проходит «рассмотрение клиники» (D-64).
- **Смена плана.** Врач открывает изменение (копия действующего плана), добавляет и убирает препараты тем же мастером,
  ещё раз смотрит итог и отправляет пациенту. Пациент видит, что добавлено и убрано, и весь новый план; **пока он не
  нажал «Принять», действует прежний**. При согласии: старые открытые приёмы снимаются, новые создаются строго на будущее,
  прошлые ответы и пропуски не меняются; врач получает сообщение. Врач может отозвать предложение. Одно изменение за раз.
  Менять можно состав препаратов; длительность идущего курса — нет (D-66).
- **Завершение.** Воркер раз в пять минут закрывает курсы, у которых прошёл последний день (по календарю пациента, с
  учётом пауз) и у каждого приёма есть исход. Пациенту — одно сообщение.
- **Устаревшее напоминание не уходит.** Перед самой отправкой воркер ещё раз спрашивает базу, его ли это напоминание:
  пауза, отмена и смена плана отменяют и то, что уже взято из очереди.
- **Миграция 0010:** таблица пауз `course_pauses` (закрывается один раз, не удаляется), не больше одного плана «в работе»
  на курс, план может быть заменён, так и не вступив в силу.
- **Проверено:** 31 тест жизненного цикла и 24 смены плана (репозитории), 23 сквозных сценария бота, 12 новых тестов
  воркера, 5 ограничений базы, правило «среза» расписания. Сорок три намеренных поломок ловятся тестами.

**Найдено и исправлено по ходу:**

- Правило этапа 3 оставляло приём, по которому напоминание уже идёт, «принадлежать старому плану». После паузы или отмены
  он остался бы без ответа навсегда, а после смены плана пациент получал бы повторы по плану, который уже заменён. Теперь
  срез один на всё: открытый приём снимается, просроченный — пропуск (D-62).
- Гонка «пациент исправляет ответ ↔ врач ставит паузу» оставляла в курсе на паузе открытый приём с напоминаниями. Ответы
  теперь удерживают строку курса, и пауза ждёт; добавлен детерминированный тест.
- Текст подтверждения отправки обещал, что курс «изменить будет нельзя», — исправлен.

**Не входит в этап (и это важно знать):**

- Сообщения пациенту и врачу о паузе, отмене, смене плана и завершении отправляются один раз, сразу после записи в базу,
  и при сбое Telegram **не повторяются**; об их недоставке никто не узнаёт (этап 10).
- Курс на паузе может стоять сколько угодно: врачу об этом не напоминают.
- Пациент не может явно отклонить изменение плана: он просто не принимает его, и врач об этом не узнаёт.
- Запрос паузы от пациента (`doctor_alert`), `CANCELLATION_REVIEW` для клиник — этапы 10–11.
- Часовой пояс идущего курса при смене пояса пациента не пересчитывается (D-45).

### Этап 10 — история, соблюдение, уведомления врачу, опекун ✅

Проверено автоматически: репозитории на настоящем Postgres, сквозные сценарии бота и воркера через поддельный Telegram.
**В живом Telegram не пройдено ничего из этого этапа.**

- **«История» у пациента.** Список курсов, у которых есть прошлое (идущие, приостановленные, завершённые, отменённые), с
  цифрой «принято вовремя N из M». Курс открывается в сводку и в записи по дням (по три дня на странице, сначала
  последние); приёмы, которые ещё не наступили, в историю не попадают.
- **Сводка курса (ТЗ §14.3).** Наступило, принято вовремя, принято с опозданием, пропущено с причиной, без ответа,
  процент; по препаратам; причины пропусков и собственные слова пациента; приёмы «по необходимости» отдельной строкой.
  **Формула печатается в каждой сводке**, показатель называется «соблюдение расписания». Снятые с расписания приёмы и
  приёмы «по необходимости» в процент не входят.
- **То же у врача:** кнопка «Соблюдение» на экране курса, по дням — с пометкой «пропущен пациентом» и причиной.
- **Приём «по необходимости» (PRN).** В «Сегодня» — строка препарата с назначением врача и счётчиком за сутки. Два
  нажатия: сначала бот показывает ограничения врача и прямо говорит, если ещё один приём выйдет за них; затем
  записывает факт. **Отметка записывается всегда** (это факт), сверх назначения — с пометкой и сообщением врачу (D-75).
  «Сутки» — любые 24 часа (D-76). Отметку можно отменить в течение часа; два нажатия подряд — одна отметка. Бот не
  советует, когда принимать: он повторяет назначение врача.
- **Что узнаёт врач (D-13).** Единица — момент расписания, а не отдельный препарат: три лекарства на 08:00 без ответа —
  один пропуск. Первый и второй подряд — отдельные сообщения; третий — одно эскалационное «свяжитесь с пациентом»;
  дальше — только сводка, не чаще раза в шесть часов. Принятый приём (в том числе с опозданием) обрывает серию.
  «Пропустить» с причиной тоже сообщается (причина — да, собственные слова пациента — нет: они только в истории).
- **Недоставленное напоминание.** Если Telegram окончательно отклонил напоминание (пациент остановил бота), врач
  получает одно сообщение в сутки на курс: «свяжитесь с пациентом другим способом» (закрывает D-60).
- **Просьба о паузе.** В «Мой курс» у идущего курса — «Попросить врача о паузе». Два нажатия; курс при этом **не
  меняется**, бот прямо говорит не прекращать лечение самостоятельно; врачу — одно сообщение в сутки.
- **Очередь сообщений врачу** (`doctor_alerts`): запись создаётся в той же транзакции, что и сам факт, отправляет воркер,
  «не менее одного раза», до восьми попыток. Перед отправкой проверяется заново: пациент успел отметить приём — сообщение
  отменяется; врач потерял статус или отменил курс — тоже.
- **Опекун (ТЗ §5.6).** Врач в списке пациентов выдаёт одноразовую ссылку (72 часа). Человек, открывший её, должен быть
  зарегистрирован в боте; он видит, кто просит и за кем наблюдать, и соглашается. **Доступ открывает только сам
  пациент** («Разрешить / Не разрешать») и может закрыть его в любой момент: «Настройки» → «Кто видит мой курс».
  Опекун видит сегодняшние приёмы с отметками и процент; не видит причин и указаний, не может ничего нажать за пациента.
- **Миграции 0011 и 0012:** очередь `doctor_alerts`, событие «отметка отменена» для PRN, ссылки для опекунов.
- **Проверено:** 22 теста очереди уведомлений, 15 PRN, 15 истории, 24 опекуна (репозитории); 24 и 17 сквозных сценариев;
  правила серии и лимитов PRN, решение «слать или нет», текст уведомления; 8 новых ограничений базы.
  Шестьдесят пять намеренных поломок ловятся тестами.

**Найдено и исправлено по ходу:**

- Отмена отметки PRN «последней по счёту» при двойном нажатии сняла бы две отметки. Кнопка теперь называет конкретную
  отметку, и повтор находит её уже отменённой.
- Один тест ядра расписания (раскладка года приёмов каждые 20 минут) падал по времени при загруженной машине; ему дан
  больший лимит. Логика не менялась.

**Не входит в этап (и это важно знать):**

- У врача нет настроек уведомлений и «тихих часов»: сообщение о пропуске придёт и ночью.
- Опекун сам сообщений о пропусках не получает: он только смотрит. Опекуну нужна своя регистрация в боте.
- Отключить опекуна может только пациент; врач — нет.
- Сообщения этапа 9 (пауза, отмена, смена плана, завершение) по-прежнему отправляются один раз, без очереди.
- Сводка для следующего врача «через три дня после завершения» (D-16) и экспорт CSV/PDF — этап 12.

### Этап 11 — панель клиники и техническая панель ✅

Проверено автоматически: репозитории на настоящем Postgres, веб-приложение — настоящими HTTP-запросами к нему на той же
базе. Собранная панель запускалась на временной локальной базе и пройдена в настоящем браузере: вход по одноразовой ссылке, выход, страницы обеих ролей, отказ на чужих страницах, подтверждение врача и закрытие инцидента формами; в журнале процесса нет ни токенов, ни строк уровня error. **Команда `/panel` в живом Telegram не пройдена.**

- **Что это.** Третий процесс, `apps/panel`: несколько страниц обычного HTML, которые собирает сервер. Скриптов в
  браузере нет совсем, и сама страница их запрещает; вся работа — ссылки и формы. Next.js из плана заменён на это
  сознательно (D-84): страниц мало, а код без клиентской части проще проверить и нечем атаковать.
- **Вход без паролей (D-85, D-86).** Сотрудник пишет боту `/panel` и получает ссылку на 5 минут, которая срабатывает один
  раз; не больше пяти ссылок за четверть часа. Открытие ссылки только показывает кнопку «Войти» (предпросмотр ссылок в
  Telegram не может её «потратить»); вход — нажатием. Сессия живёт 12 часов; cookie недоступна скриптам и не уходит с
  чужих сайтов; от ссылки и от сессии в базе лежат только хэши. Для того, кто не сотрудник, команды `/panel` «нет»: бот
  отвечает как на любую неизвестную команду и не выдаёт, кто сотрудник.
- **Права читаются из базы на каждый запрос (D-87).** Отозвали роль — следующий же запрос получает страницу входа; ссылка,
  выданная до отзыва, не сработает. Это же перепроверяет слой данных, независимо от страниц.
- **Технический администратор:** заявки врачей (подтвердить с пометкой «что проверено», отозвать; врачу уходит
  сообщение в бот), клиники и их сотрудники (назначить по Telegram id, отозвать), «Состояние сервиса» (очереди по
  состояниям, просрочка, зависшее, сбои по кодам, задержка отправки — медиана и 95%), технические инциденты, журнал
  аудита (кто — короткой ссылкой, что сделано, какие поля; значений в журнале нет). **Имён пациентов и назначений на этих
  страницах нет.**
- **Сотрудник клиники** (ресепшн или администратор клиники) видит только свою клинику: её врачей, список курсов без
  содержимого (пациент, врач, состояние, даты) и её инциденты. Имя пациента показывается, пока клиника его ведёт.
  Каждое открытие списка пишется в аудит. Страницы технического администратора и чужой клиники отвечают отказом.
- **Инциденты.** Операционные — клинике: напоминание не доставлено (раз в сутки на курс) и три приёма подряд не приняты;
  создаются в той же транзакции, что и сообщение врачу. Закрываются с отметкой «что сделано» (результат звонка; шифруется,
  до 500 символов); бот сам никому не звонит (D-18). Технические — администратору: очередь отстаёт больше чем на 10
  минут, отправка зависла, пропуски записываются с опозданием. Их открывает сверка воркера раз в пять минут, не чаще
  одного каждого вида в сутки; в них только числа.
- **Защита страниц.** Каждая форма несёт токен сессии (CSRF) и без него отклоняется; всё, что вводили люди, выводится
  как текст; запрещены кеширование, встраивание во фрейм и любые скрипты; принимаются только формы. Журнал запросов
  панели пишет путь без параметров: в адресе одноразовой ссылки лежит её токен.
- **Командная строка:** `pnpm admin list-clinics | add-staff | revoke-staff` — то же самое без браузера.
- **Воркер:** сверка очередей раз в пять минут; раз в час забывает ссылки и сессии панели, истёкшие больше суток назад.
- **Миграция 0013:** `panel_logins`, `panel_sessions`, `incidents`.
- **Проверено:** 26 тестов репозиториев панели и инцидентов, 37 тестов веб-приложения (вход, срок и выход, «каждая роль
  видит только своё», CSRF на каждой форме, вывод введённого как текста, отзыв роли посреди запроса), 8 тестов сборки
  страниц, 7 сценариев команды `/panel`, сверка и уборка в воркере, 14 тестов командной строки, 6 групп ограничений базы.
  Намеренных поломок поймано: 78 из 78.

**Найдено и исправлено по ходу:**

- Стандартный журнал запросов веб-сервера пишет адрес целиком, то есть вместе с токеном одноразовой ссылки. В панели он
  выключен; вместо него одна строка на запрос с путём без параметров. Есть тест, который ищет токен в журнале.
- Отзыв сотрудника клиники из панели отвечал «готово», даже если отзывать было нечего. Теперь — «не найдено».

**Не входит в этап (и это важно знать):**

- **Клиника в MVP — это частная практика одного врача (D-26).** Создать клинику из нескольких врачей или перевести врача
  в другую клинику нельзя, поэтому «ресепшн клиники» сейчас — помощник одного врача.
- Ресепшн и администратор клиники видят и могут одно и то же; подтверждать врачей может только технический администратор.
- **Об инцидентах сообщения приходят с этапа 14.** Если воркер не работает, технический инцидент открыть некому (но «Состояние сервиса» считает числа в момент открытия страницы и отставание покажет).
- HTTPS панель сама не делает: это задача обратного прокси при развёртывании (этап 15); вне `APP_ENV=local` адрес
  панели обязан быть `https://`. Ограничения частоты в панели с этапа 14 есть.
- Списки ограничены 200 строками (журнал аудита — страницами по 100); поиска, экспорта и просмотра курса по дням нет.
- Сессию нельзя закрыть «на всех устройствах» одной кнопкой: только выход в каждом браузере или отзыв роли.

### Этап 12 — экспорт CSV/PDF ✅

Проверено автоматически: данные отчёта — на настоящем Postgres, сами файлы — тестами их содержимого, путь «кнопка →
документ в чате» — сквозными сценариями через поддельный Telegram. PDF (на русском и узбекском) и CSV я открыл и
просмотрел. **В живом Telegram файл не отправлялся; в настоящем Excel CSV не открывался.**

- **Где это.** Под сводкой «Соблюдение» (у пациента — «История» → курс; у врача — курс → «Соблюдение») две кнопки:
  «📄 Отчёт PDF» и «📊 Таблица для Excel (CSV)». Файл приходит **документом в чат того, кто нажал**; ссылки на
  скачивание не существует, на сервере файл не хранится (D-95).
- **Кто может.** Те же двое, кто читает сводку: сам пациент и врач, который его сейчас ведёт. Чужой врач, коллега из
  той же клиники, ресепшн, технический администратор и опекун файл не получат; врач, переставший вести пациента, — тоже.
- **Что в файле.** Пациент, врач, состояние и даты курса, когда и кем запрошен; итог (наступило, вовремя, с опозданием,
  пропущено, без ответа, процент) и **формула процента словами**; то же по каждому препарату; приёмы «по
  необходимости»; причины пропусков; паузы; и **каждый приём**: дата, время, препарат, доза, исход, когда отмечен,
  причина и комментарий пациента. Будущие приёмы и снятые с расписания в файл не входят.
- **Отчёт воспроизводим.** В список попадает каждый приём, у которого есть исход (в том числе принятый чуть раньше
  времени), поэтому процент можно пересчитать по строкам самого файла; это проверяет тест.
- **CSV для Excel:** UTF-8 с меткой порядка байтов (кириллица не превращается в «кракозябры»), разделитель — точка с
  запятой, десятичная запятая (`62,5`), как ждёт Excel с русскими и узбекскими настройками.
- **Защита того, кто открывает файл.** Название препарата и слова пациента — это текст, набранный людьми. Если такая
  ячейка начинается с `=`, `+`, `-` или `@`, Excel выполнил бы её как формулу на компьютере врача; такие ячейки
  обезврежены апострофом (D-99).
- **PDF:** A4, шрифт с кириллицей и узбекской латиницей встроен в сам файл, длинный курс уходит на следующие страницы с
  повторением шапки таблицы, внизу «Страница N из M». Символ, которого в шрифте нет (эмодзи в названии), печатается как
  «?», отчёт всё равно выходит.
- **Язык** файла — язык того, кто его запросил; время — по часовому поясу курса, и это написано в файле.
- **Учёт.** Каждая выдача записывается: кто, какой курс, какой формат, когда (таблица `course_exports` и журнал аудита,
  без содержимого). Не больше 10 файлов в час на человека; одновременные нажатия лимит не обходят.
- **Если Telegram не принял файл**, человек получает сообщение об этом, а не тишину.
- **Миграция 0014:** `course_exports` (только добавление).
- **Проверено:** 35 тестов отчёта (слова и таблицы, CSV, PDF), 11 тестов данных и учёта, 9 сквозных сценариев в боте,
  кодек кнопок, ограничения базы. Намеренных поломок поймано: 72 из 72. Одна сначала выжила (ячейка, начинающаяся с табуляции) и привела к новому тесту.

**Найдено и исправлено по ходу:**

- Первый вариант давал получить строки отчёта методом, который не спрашивал, кто просит: проверка была только у
  вызывающего. Метод убран внутрь, наружу торчит только тот, что проверяет права.
- Приём, отмеченный «принят» раньше своего времени, считался в проценте, но в список по дням не попадал: процент нельзя
  было бы пересчитать по файлу. В файл он теперь входит.

**Не входит в этап (и это важно знать):**

- **Файл остаётся в чате Telegram** у того, кто его запросил, и дальше этот человек сам решает, кому его переслать; в
  подписи к файлу об этом сказано.
- Отчёт только по одному курсу; сводного отчёта по пациенту или по всем пациентам врача нет.
- Выгрузки журнала аудита файлом нет: в панели он только просматривается (ТЗ §14.2 просит и экспорт).
- Файл собирается прямо во время нажатия. Курс на год с четырьмя приёмами в день — это PDF страниц на пятьдесят и
  пара секунд ожидания.
- Из-за встроенного шрифта собранный бот вырос с 4 до 8 МБ.
- Сводка «для следующего врача через три дня после завершения» (D-16) — этап 13.

### Этап 13 — приватность, хранение, бэкапы ✅

Проверено автоматически: правила — на настоящем Postgres, раздел бота — сквозными сценариями через поддельный Telegram,
резервные копии — настоящим восстановлением в отдельную базу. Команды копии и пробного восстановления я запускал на
локальной базе. **В живом Telegram раздел не пройден. Копия на большой базе не делалась: локальная почти пуста.**

- **«Настройки» → «Согласие и данные».** Когда и на какую редакцию текста дано согласие; «Мои врачи»; «Отозвать
  согласие»; «Удалить мои данные». Всё, что нельзя отменить одним нажатием, спрашивается дважды, и экран прямо говорит,
  что остановится и что сохранится.
- **Отключиться от врача (закрывает D-31).** Курсы, которые назначил этот врач, останавливаются сразу (напоминаний больше
  нет), врач перестаёт видеть пациента и получает сообщение. Другие врачи и их курсы не затрагиваются.
- **Отозвать согласие (D-103).** Сервис для человека прекращается: все курсы остановлены, врачи и опекуны теряют доступ,
  бот на любое сообщение отвечает только одним: как дать согласие снова. **Данные при этом не удаляются.** Согласие
  можно дать заново: аккаунт возвращается, врачей нужно подключать заново.
- **Удалить мои данные (D-104, D-105).** Доступ закрывается сразу, как при отзыве согласия. Через 30 дней воркер
  **обезличивает** записи: стирает имя, идентификатор Telegram и весь свободный текст (слова пациента о пропусках,
  указания врача к препаратам, отметки о звонках, пометку врача в приглашении) и удаляет сводки. Остаются строки курса
  без человека — чтобы сходились журнал и отчётность. До этого дня запрос можно отменить одной кнопкой. После
  обезличивания тот же человек может зарегистрироваться заново — как новый.
- **Врач или сотрудник** не может отозвать согласие или удалить себя кнопкой: от него зависят чужие курсы. Бот говорит
  обратиться к администратору (D-106).
- **Сводка завершённого курса (ТЗ §12.1, D-108).** Через три дня после окончания курса воркер составляет краткую
  сводку: даты, препараты, цифры соблюдения. Без указаний, причин и комментариев. Оригинал при этом не удаляется.
- **Сводки для нового врача (D-109).** Пациент в «Мои врачи» включает «Показать прошлые курсы» для конкретного врача;
  у того в списке пациентов появляется «Прошлые курсы». Пациент может закрыть это в любой момент; отключение от врача
  закрывает само. Каждое чтение пишется в аудит.
- **Резервные копии (D-111).** `pnpm db:backup <папка> --keep N`: вся база одним снимком, сжатая и зашифрованная
  **отдельным ключом** `BACKUP_KEY` (не тем, которым зашифрованы поля; конфигурация это проверяет). Файл, который
  обрезан, изменён или открыт не тем ключом, отклоняется.
- **Пробное восстановление.** `pnpm db:restore-drill <файл>`: создаёт временную базу, восстанавливает в неё копию,
  сверяет **каждую таблицу по числу строк и по контрольной сумме содержимого**, проверяет, что зашифрованные поля
  читаются текущими ключами, и удаляет временную базу. `pnpm db:restore <файл>` — то же в пустую базу по-настоящему.
- **Миграция 0015:** `deletion_requests`, `course_summaries`, отметка «пациент открыл прошлые курсы» у связи с врачом.
- **Проверено:** 19 тестов правил приватности, 12 сквозных сценариев бота, 11 тестов резервных копий, воркер, конфиг,
  ограничения базы, кодек кнопок. Намеренных поломок поймано: 89 из 92. Шесть сначала выжили и привели к новым проверкам; три оставшиеся — равнозначные правки: то же условие проверяется вторым, независимым предохранителем.

**Найдено и исправлено по ходу:**

- Моя правка защиты журналов (чтобы обезличивание могло стереть текст) ломала саму защиту у таблиц без такого поля:
  попытка изменить журнал аудита отклонялась не тем отказом. Поймали прежние тесты ограничений базы; исправлено.
- Сводка составлялась и для человека, который уже попросил удалить данные. Теперь для отозвавшего согласие сводки не
  составляются, пока он не даст согласие снова.
- В этой среде нет `pg_dump`, и в образе приложения его тоже нет. Резервная копия сделана средствами самого приложения:
  так её можно восстановить и сверить здесь и сейчас, а не «когда-нибудь в Docker».

**Не входит в этап (и это важно знать):**

- **Копию никто не запускает по расписанию.** Команда есть, а ежедневный запуск и вынос файла на другой носитель —
  задача того, кто разворачивает сервис (этап 15). Ключ `BACKUP_KEY` нужно хранить отдельно от копий: без него и без
  `ENCRYPTION_KEYS` копию не прочитает никто, включая вас.
- **Восстановление из старой копии возвращает уже удалённые данные.** Воркер пишет в журнал идентификатор каждого
  обезличенного аккаунта; после восстановления удаления за это время нужно выполнить заново. Сейчас это ручной шаг.
- Восстановление требует подключения суперпользователя базы и идёт только в пустую базу.
- Сроки хранения медицинских записей юристом не заданы (D-16): **по сроку ничего медицинского не удаляется**, только по
  запросу человека.
- Сообщение врачу «пациент отключился» уходит один раз, без повторов (как сообщения этапа 9).
- Удалить аккаунт врача или сотрудника можно только вручную: инструмента для этого нет.
- На экране согласия показаны дата и редакция текста, но сам текст заново не выводится.
- Тексты согласия и сама процедура удаления не проверены юристом.

### Этап 14 — наблюдаемость и защита ✅

Проверено автоматически и нагрузочным прогоном на локальной базе (в реальном времени, через настоящий код воркера,
с Telegram, который отвечает за 100 мс). Собранный воркер запускался, его страницу метрик я читал. **Настоящая
нагрузка (тысячи человек) и живой Telegram не проверялись.**

- **Пик напоминаний — найденная проблема.** Воркер слал напоминания по одному, подряд: 6–12 в секунду. Пик в 1000
  человек (всем врачи назначили 08:00) не укладывался в минуту: хвост получил бы напоминание через две-три минуты. Теперь
  (D-115…D-117): до 10 отправок одновременно, но не быстрее 25 в секунду на весь бот (лимит Telegram около 30 —
  превышение наказывается ответом 429 и паузой для всех); очередь разбирается раундами подряд до 20 секунд; на ответ 429
  ждут все отправители, а не только отказанный. **В прогоне 150 напоминаний на одну секунду ушли за ~6 секунд, у
  последнего задержка меньше 7,5 с, у 95-го процентиля меньше 6,5 с; больше 27 сообщений в любую секунду не уходило.**
  Требование ТЗ — «в пределах минуты от слота»: при этом темпе в минуту укладываются ~1500 напоминаний на один и тот же
  момент.
- **Оповещения об инцидентах (D-118).** Закрыт пробел этапа 11: раньше инцидент видел только тот, кто открыл панель.
  Теперь воркер присылает одно короткое сообщение «Инцидент: <вид>. Подробности — в панели»: техническим администраторам
  о технических, сотрудникам клиники об операционных. Ни имени пациента, ни препарата, ни числа в сообщении нет. Не
  дошло ни до кого — повтор через 2 минуты, всего 6 попыток; никому слать — остаётся панель. В журнал идёт только число
  неудач.
- **Алерты проверены искусственными сбоями.** Воркер «остановлен» (напоминания просрочены, приём без записи) — техадмины
  получили два сообщения, один раз, каждый на своём языке; воркер «умер» с взятым напоминанием — «отправка зависла»;
  пациент заблокировал бота — сообщение персоналу своей клиники и никому больше; три пропуска подряд — персоналу
  клиники; Telegram лежит — повторы с паузой и отказ после шести; Telegram вернулся — сообщение доходит один раз; один
  получатель отказывает — остальные получили.
- **Метрики (D-119).** У воркера страница `/metrics` в формате Prometheus: глубина очередей напоминаний и сообщений врачу
  по состояниям, просрочка и возраст самого старого, зависшее, сбои по кодам, количество отправленного и задержка «срок
  → отправка» (медиана и 95-й процентиль), приёмы без записи о пропуске, открытые инциденты по видам, курсы и врачи по
  состояниям. Только числа и машинные коды. Страница под `Authorization: Bearer <METRICS_TOKEN>`; без токена в настройках
  страницы нет. Те же числа показывает «Состояние сервиса» в панели.
- **Защита от частых запросов (D-120).** Панель: не больше 240 запросов в минуту и 12 попыток входа за 5 минут с одного
  адреса; сверх — страница с 429 и `Retry-After`, база не трогается; пробы и стили не считаются. Вход по одноразовой
  ссылке с адреса, исчерпавшего лимит, ссылку **не тратит**. Адрес берётся из `X-Forwarded-For` только при
  `PANEL_TRUST_PROXY=true` (за обратным прокси); иначе заголовок — то, что написал сам вызывающий, и игнорируется.
- **Проверки безопасности (D-121, D-122).** Тест `hygiene.test.ts` на каждом прогоне: в файлах репозитория (в том числе
  ещё не закоммиченных) нет ничего, похожего на токен бота (шаблон учитывает, что токен может кончаться на «-»), на
  приватный ключ и на настоящий ключ шифрования; `.env` не в git; в коде нет `parse_mode`, `eval`, `child_process`;
  запросы из строк (`.unsafe(`) есть ровно в четырёх файлах (раннер миграций, копии, локальная база); `process.env`
  читается только в `packages/config`; панель не разрешает скрипты. Такой тест поймал бы токен, попавший в репозиторий
  на этапе 3. Проверка зависимостей `pnpm audit --prod`: уязвимостей нет; в CI она теперь шаг. Для инструментов сборки
  одно замечание низкой важности (esbuild): в образы не попадает.
- **Конфигурация:** `METRICS_TOKEN` (24–200 символов), `PANEL_TRUST_PROXY` (`true`/`false`).
- **Миграция 0016:** счётчик попыток и время последнего оповещения у инцидента.
- **Проверено:** 12 тестов оповещений и сбоев, 3 нагрузочных, 5 темпа отправки, 4 ограничителя, 5 новых в панели,
  метрики и их страница, 8 проверок гигиены, 3 теста настроек. Намеренных поломок поймано: 53 из 53. Восемь сначала выжили и привели к новым проверкам: слабая проверка паузы, запасная защита от бесконечных повторов, рост таблицы адресов, проверки гигиены не видели новых файлов.

**Найдено и исправлено по ходу:**

- Узкое место отправки (см. выше). Попутно тесты, которые «вмешиваются» между двумя напоминаниями, теперь идут строго
  по одному: при параллельной отправке обе проверки «напоминание ещё действует» уже пройдены к этому моменту. Это
  осознанное окно в миллисекунды (оно было и раньше, между проверкой и вызовом Telegram), его не закрыть без блокировки
  на время сетевого вызова.
- Мутационная проверка показала: проверки гигиены смотрели только файлы, уже известные git, и пропустили бы токен в
  новом, ещё не закоммиченном файле. Теперь смотрят и их.
- Шаблон токена с границей слова пропускал токен, оканчивающийся на «-» (так бывает). Исправлен.

**Не входит в этап (и это важно знать):**

- **Нет доставки оповещений кроме Telegram:** если Telegram недоступен, а метрики никто не читает, о беде узнают из
  панели. Внешний мониторинг (кто читает `/metrics`, кому звонить ночью) настраивается при развёртывании (этап 15).
- Ограничений частоты на сообщения самого бота нет, кроме прежних (20 в 10 секунд на человека, приглашения, экспорт,
  `/panel`). Ограничение страницы метрик — только токен.
- Нагрузка проверена на 150 одновременных напоминаниях и на локальной базе; тысячи и настоящий Telegram с его ответами
  и лимитами не проверялись. При росте лимит 25 в секунду и батч 100 придётся пересмотреть.
- Сообщение об инциденте уходит не через очередь с вечными повторами: после шести неудач остаётся только панель.
- Ежедневная сверка (в плане этапа) сделана как сверка раз в пять минут (этап 11); отдельной ежедневной нет.
- Это не полный аудит безопасности: нет проверки глубиной «злоумышленник против настоящего сервера», перебора
  паролей (паролей нет), проверки TLS (его даёт прокси). Настоящая проверка — до пилота.

### Этап 15 — пилот 🟦

Код и руководство для запуска готовы; **условие готовности этапа (все пункты «Перед пилотом обязательно утвердить»
из ТЗ §20) выполнить может только человек**. Пока этап не закрыт, настоящих пациентов в сервис не пускать.

**Сделано (проверено тестами на настоящей базе и запуском собранной программы):**

- **`ops.cjs` — команды оператора в образе бота** (D-123): `migrate up|status`, `backup <папка> [--keep n]`,
  `drill <файл>`, `restore <файл> [--yes-this-is-production]`, `preflight [--backups <папка>] [--offline]`. Раньше
  миграции и копии запускались только из исходников через `tsx`; на сервере их нет. Логика вынесена в
  `packages/db/src/ops.ts` (`pnpm db:*` стали тонкими обёртками), миграции лежат в образе (`/app/migrations`).
  `migrate down` в production отказывается; неверное число шагов и `--keep` отклоняются до действия.
- **Проверка готовности `preflight`** (D-124, `apps/bot/src/ops/preflight.ts`): одна команда вместо пяти мест —
  настройки (не `local`, ключи не `dev…`, `BACKUP_KEY` задан, webhook, панель на https), Telegram (`getMe`,
  `getWebhookInfo`: адрес, ошибки доставки, очередь обновлений), база (UTF-8, миграции и контрольные суммы, активный
  технический администратор, подтверждённые врачи, опоздавшие больше чем на 10 минут и зависшие напоминания) и свежесть
  последней копии (не старше 26 часов). Печатает `[ ok ]`/`[warn]`/`[FAIL]`/`[skip]` и `ready`/`NOT READY`, код выхода
  1 при любом FAIL. Ничего не меняет; значений секретов и текстов ошибок Telegram в выводе нет (адрес запроса с токеном).
- **Файлы для сервера** (D-125, D-126, `deploy/`): `docker-compose.prod.yml` (база без портов наружу → одноразовый
  `migrate` → `bot`, `worker`, `panel`, `backup`; снаружи только Caddy), `Caddyfile` (HTTPS сам; миру открыты
  `POST /telegram/*` бота и панель, `/healthz` и `/metrics` внутри сети), `.env.production.example` (имена всех
  секретов, значений нет; тест гигиены следит, что их там не появится). Ежесуточная копия — контейнер `backup`;
  `healthy`, пока свежий файл не старше 26 часов. Файл разобран `docker compose config`.
- **Руководство `docs/PILOT.md`** (D-127): что получить до запуска, развёртывание по шагам, ежедневные дела, откат и

### Этап 16 — админка внутри бота ✅

Владелец попросил, чтобы администрирование было в самом чате, а не только в веб-панели. Проверено тестами на настоящей
базе с поддельным Telegram и мутационной проверкой; **в настоящем Telegram раздел вживую не нажимался.**

- **Кто видит.** «⚙️ Админка» в меню и `/admin` — только у действующего технического администратора. Остальным команды не
  существует, а кнопки раздела ничего не делают (проверено нажатием чужих кнопок). Право решает база при каждом
  нажатии: снятый администратор со старыми кнопками и недописанным вопросом не делает ничего (`ARCHITECTURE` 9.2).
- **Заявки врачей и врачи.** Список с числом на кнопке, карточка (что написал, что проверено, Telegram id, дата в местном
  времени). «Подтвердить» просит одним сообщением написать, что проверено (3–200 символов) и сохраняет это как основание
  подтверждения (D-129); врач получает сообщение на своём языке. «Отозвать статус» — после второго вопроса, доступ врача
  закрывается сразу.
- **Состояние и инциденты.** Очереди (опоздавшие, зависшие), отправленное за сутки, приёмы без записи о пропуске, число
  аккаунтов и врачей по состояниям, открытые инциденты по виду и времени. Только числа и коды, без имён.
- **Администраторы (D-128).** Список, «➕ Добавить» по Telegram id (человек должен сначала написать боту `/start`; ему
  приходит сообщение), «Снять права» после второго вопроса (человеку тоже приходит сообщение). Себя снять нельзя,
  последнего тоже; двое, снимающие друг друга одновременно, оставят одного (блокировка строк). Командная строка
  `grant-admin` остаётся способом выдать первую роль.
- **Миграция 0017:** поток разговора `ADMIN` (вопросы «что проверено» и «чей id»).
- **Репозиторий `platform`:** `isTechAdmin`, `grantTechAdmin` (система или администратор), `listTechAdmins`,
  `revokeTechAdmin` (`REVOKED` / `NOT_ADMIN` / `SELF` / `LAST`); всё в журнале аудита.
- **Проверено:** 24 теста раздела (видимость, чужие кнопки, подтверждение с заметкой и без, отмена, снятый
  администратор, длинные списки, язык сообщений), 10 тестов правил администраторов (в том числе гонка двух снятий,
  повторённая трижды), тесты кнопок. **Намеренных поломок поймано: 54 из 57.** Пятнадцать сначала выжили: двенадцать привели к новым проверкам, три остались: отказ базы в долю секунды между проверкой меню и вызовом, текст «последний администратор» (достижим только в такой же гонке) и перепутанные числа очереди сообщений врачам (в тестовой базе они нулевые).
- **Оформление репозитория:** `README.md` переписан (схемы, быстрый старт, состояние), добавлены `CONTRIBUTING.md`,
  `SECURITY.md`, шаблоны issue и pull request.

- **Доработано по ревью кода (2026-10-06):** карточка врача открывается одним запросом
  (`clinicians.getApplication`) вместо перебора трёх списков; флаги меню «подопечные» и «админка» читаются одним
  запросом `users.menuFlags` вместо двух на каждое сообщение; `grantTechAdmin` говорит, что сделал
  (`GRANTED` / `ALREADY` / `NO_ACCOUNT`) — лишний запрос из бота убран; карточка отозванного врача предлагает
  «♻️ Восстановить статус» вместо «Подтвердить» (D-130). Плюс тесты на оба новых метода.

**Не входит в этап:**

- Раздел вживую в Telegram не нажимался; узбекские тексты раздела не читал носитель языка.
- Нет настроек сотрудников клиники в чате (их назначают командой `add-staff` или в веб-панели); «отклонить заявку»
  врача отдельной кнопкой нет: заявка остаётся ждущей или подтверждается; отзыв — только у подтверждённого.
- Администратор не видит журнал аудита в чате (он есть в веб-панели).
- Назначение администратора из чата — смягчение прежнего правила (D-128); если нужно строже, достаточно убрать кнопку и
  оставить командную строку.

| `ENCRYPTION_KEYS`         | ключи прикладного шифрования, `id:base64(32 байта)` через запятую                                                                                       | всем                            |
| `HTTP_PORT`               | порт процесса; по умолчанию bot 3000, worker 3001, panel 3002                                                                                           | нет                             |
| `LOG_LEVEL`               | уровень логирования                                                                                                                                     | нет                             |
| `TELEGRAM_BOT_TOKEN`      | токен бота от @BotFather (отдельный бот на окружение); воркеру нужен тот же, чтобы отправлять напоминания                                               | боту и воркеру                  |
| `TELEGRAM_MODE`           | `polling` (по умолчанию в local) или `webhook` (по умолчанию иначе)                                                                                     | нет                             |
| `TELEGRAM_WEBHOOK_SECRET` | 16–256 символов `A-Za-z0-9_-`; проверка заголовка `X-Telegram-Bot-Api-Secret-Token`                                                                     | webhook                         |
| `PUBLIC_BASE_URL`         | `https://`-адрес, доступный Telegram, без пути                                                                                                          | webhook                         |
| `PANEL_BASE_URL`          | адрес, по которому сотрудники открывают панель, без пути (локально `http://localhost:3002`, иначе только `https://`); боту — чтобы строить ссылку входа | панели; боту — если панель есть |
| `BACKUP_KEY`              | ключ резервных копий, `id:base64(32 байта)`; не должен совпадать ни с одним из `ENCRYPTION_KEYS`                                                        | командам копий                  |
| `METRICS_TOKEN`           | пароль страницы `/metrics` у воркера, 24–200 символов `A-Za-z0-9_-`; без него страницы нет                                                              | нет                             |
| `PANEL_TRUST_PROXY`       | `true`, если перед панелью стоит обратный прокси (адрес берётся из `X-Forwarded-For`)                                                                   | за прокси                       |

Для сервера пилота есть своя заготовка `deploy/.env.production.example` (имена секретов, адреса `BOT_HOST`, `PANEL_HOST`,
`ACME_EMAIL`, пароль базы, `BACKUP_AT`, `BACKUP_KEEP`); значения вносятся на сервере в `.env.production`.

Первый ключ из `ENCRYPTION_KEYS` шифрует, все расшифровывают; в `.env.example` лежит одноразовый `dev1` (вне `local` ключи
`dev…` запрещены). Polling вне `local` запрещён. Панели токен бота не обязателен: с ним она сообщает врачу о подтверждении.

## 7. Команды запуска и проверок

Нужны Node 24 и pnpm 9 (`corepack enable`). Первый запуск: `pnpm install`.

```bash
pnpm check           # format:check + lint + typecheck + test (то же, что CI, кроме build)
pnpm build           # собрать dist/main.cjs у bot, worker и panel
pnpm test            # только тесты
pnpm format          # применить Prettier
```

Живой бот на вашей машине (без Docker; два терминала):

```bash
cp .env.example .env               # затем впишите TELEGRAM_BOT_TOKEN= (токен тестового бота от @BotFather)
pnpm dev:db                        # терминал 1: Postgres 16 на 127.0.0.1:5433, данные в .dev-pg/
pnpm db:migrate                    # терминал 2, один раз
pnpm dev:bot                       # бот: polling, :3000
```

Потом откройте своего бота в Telegram и отправьте `/start`. Токен лежит только в `.env` (он в `.gitignore`).

Врачи и администратор (после запуска бота и `/start` в нём у вас должен быть аккаунт):

```bash
pnpm admin grant-admin <ваш-telegram-id>                         # один раз: сделать свой аккаунт администратором
pnpm admin list-doctors --by <ваш-telegram-id>                   # кто подал заявку (id, что написал, Telegram id)
pnpm admin verify-doctor <user-id> --by <ваш-telegram-id> --reference "лицензия UZ-… проверена"
pnpm admin revoke-doctor <user-id> --by <ваш-telegram-id>        # отозвать: доступ врача закрывается сразу
```

Ваш Telegram id покажет любой бот вроде @userinfobot. Проверка врача, подключение пациента и подтверждение целиком идут в
чате: заявка («Для врачей» в меню) → `verify-doctor` → «Пригласить пациента» → ссылка → второй аккаунт Telegram открывает её
и соглашается → врач подтверждает → «Новый курс» → препараты → «Отправить пациенту» → пациент видит назначение →
«Начать курс» → «Да, начать» → «Сегодня» показывает приёмы. Напоминания отправляет воркер: в третьем терминале
запустите `pnpm dev:worker` (ему нужен тот же `TELEGRAM_BOT_TOKEN` из `.env`). Чтобы не ждать, назначьте приём на
ближайшие минуты: в мастере выберите «Своё время». Дальше у врача: «Для врачей» → «Курсы» → курс → «Приостановить»,
«Возобновить», «Изменить план» (пациенту придёт вопрос с кнопкой «Принять новый план»), «Отменить курс»,
«Соблюдение» (под сводкой — «Отчёт PDF» и «Таблица для Excel»: файл придёт в этот же чат). Сообщения врачу о
пропусках тоже отправляет воркер. Опекун: «Для врачей» → «Пациенты» → «Опекун: …» →
ссылку открывает третий аккаунт (уже зарегистрированный в боте) → пациент разрешает → у опекуна в меню «Подопечные».
В собранном образе та же команда: `node admin.cjs list-doctors --by <id>`.

Панель для сотрудников (четвёртый терминал; в `.env` должна быть строка `PANEL_BASE_URL=http://localhost:3002`, после
неё бота нужно перезапустить):

```bash
pnpm dev:panel                                                    # панель на http://localhost:3002
pnpm admin list-clinics --by <ваш-telegram-id>                    # клиники (практики врачей) и их сотрудники
pnpm admin add-staff <clinic-id> <telegram-id> --role RECEPTION --by <ваш-telegram-id>
pnpm admin revoke-staff <staff-id> --by <ваш-telegram-id>
```

Администратор (после `grant-admin`) или сотрудник клиники пишет боту `/panel`, открывает ссылку из ответа в браузере на
этом же компьютере и нажимает «Войти». Ссылка живёт 5 минут и срабатывает один раз. Подтверждать врачей и назначать
сотрудников теперь можно и в панели («Врачи», «Клиники и сотрудники»).

Локальная разработка с Docker Desktop:

```bash
cp .env.example .env
docker compose up -d postgres      # Postgres на 127.0.0.1:5433
pnpm dev:bot                       # :3000, перезапуск при правках
pnpm dev:worker                    # :3001
pnpm dev:panel                     # :3002
docker compose up --build          # или всё в контейнерах
```

Тесты и база:

```bash
pnpm test:unit       # быстро (~1 с), без базы
pnpm test:db         # тесты на Postgres; первый запуск поднимает встроенный Postgres 16 (~10 с)
pnpm db:status       # состояние миграций (нужен .env и доступная БД)
pnpm db:backup <папка> --keep 14      # зашифрованная копия базы (нужен BACKUP_KEY в .env); оставить 14 последних
pnpm db:restore-drill <файл.mcbk>     # пробное восстановление во временную базу со сверкой каждой таблицы
pnpm db:restore <файл.mcbk>           # настоящее восстановление: только в пустую базу, суперпользователем
# метрики воркера (нужен METRICS_TOKEN в .env воркера): curl -H "Authorization: Bearer $METRICS_TOKEN" http://127.0.0.1:3001/metrics
pnpm db:migrate      # применить; pnpm db:rollback [шагов] — откат (в production запрещён)
```

На сервере те же действия делает одна программа из образа бота (`docs/PILOT.md`):

```bash
node ops.cjs migrate up | status
node ops.cjs backup /backups --keep 14 | drill <файл> | restore <файл> [--yes-this-is-production]
node ops.cjs preflight --backups /backups     # готова ли установка; код выхода 1, если нет
pnpm ops preflight --offline                   # то же из исходников (без вопросов к Telegram)
```

Если в окружении задан `DATABASE_URL`, `pnpm test:db` использует этот сервер (нужен суперпользователь: каждый тестовый файл
создаёт и удаляет свою базу `mc_test_*`). Так делает CI; без переменной тесты не трогают ваши данные.
