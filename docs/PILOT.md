# Пилот: как запустить, что утвердить, когда можно пускать людей

Документ для владельца и для того, кто ведёт сервер. Что здесь **сделано в коде** (проверки, файлы для сервера,
резервные копии) и что **остаётся людям** (клиника, юрист, ключи, сервер) — разделено явно. Код не может
утвердить медицинские тексты и не заменяет юриста.

Три вещи, о которых нужно знать сразу:

1. **Проверено тестами** (на настоящей базе, с поддельным Telegram): проверка готовности, миграции, резервные копии.
   **Не проверено вживую**: `docker compose up` на сервере, HTTPS через Caddy, настоящая доставка сообщений врачу и
   пациенту, `/panel` в Telegram, нагрузка. Первый запуск на сервере — это и есть первая живая проверка; раздел 3
   говорит, как её пройти и как откатиться.
2. Токен бота, попавший в историю git на вашем компьютере, нужно **отозвать** (`/revoke` у @BotFather) и выпустить
   новый — до пилота, а не после. На сервер идёт только новый.
3. Ключ `ENCRYPTION_KEYS` — единственный способ прочитать имена и назначения пациентов. Потеряли ключ — потеряли данные,
   даже если резервные копии целы. Он должен лежать в менеджере паролей **и** отдельно от сервера.

## 1. Что нужно получить до первого запуска

| Что                          | Откуда                                                                                                 | Кто            |
| ---------------------------- | ------------------------------------------------------------------------------------------------------ | -------------- |
| Сервер                       | VPS с Ubuntu 22.04+ или 24.04, 2 ГБ памяти, 20 ГБ диска, Docker + Compose, порты 80 и 443              | вы             |
| Два имени                    | например `bot.<домен>` и `panel.<домен>`, обе записи A указывают на IP сервера                         | вы             |
| Новый бот                    | @BotFather → `/newbot`, имя и описание бота — тексты утверждает клиника (раздел 5)                     | вы             |
| `ENCRYPTION_KEYS`            | команда в `deploy/.env.production.example`; id не начинается с `dev`                                   | вы             |
| `BACKUP_KEY`                 | та же команда, **другое** значение                                                                     | вы             |
| `TELEGRAM_WEBHOOK_SECRET`    | команда в том же файле                                                                                 | вы             |
| `METRICS_TOKEN`, пароль базы | любая длинная случайная строка                                                                         | вы             |
| Место для копий вне сервера  | второй сервер, облачное хранилище или ваш компьютер: резервные копии лежат на том же диске, что и база | вы             |
| Список из раздела 5          | утверждённые решения, тексты, юридическая проверка                                                     | клиника, юрист |

Значения секретов не пересылайте ни в чат, ни по почте, ни мне. Они вносятся прямо на сервере в файл
`.env.production` (он в `.gitignore`).

## 2. Что где лежит

| Файл                             | Назначение                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `deploy/docker-compose.prod.yml` | всё, что запускается на сервере: база, миграция, бот, воркер, панель, копии, Caddy                       |
| `deploy/Caddyfile`               | HTTPS (сертификат Caddy получает и продлевает сам) и маршруты: миру открыты только webhook бота и панель |
| `deploy/.env.production.example` | образец настроек сервера                                                                                 |
| `apps/bot/src/ops/` → `ops.cjs`  | команды оператора: `migrate`, `backup`, `drill`, `restore`, `preflight`                                  |

Что компоуз делает сам: база (внутри сети, порты наружу не открыты) → контейнер `migrate` применяет миграции и
завершается → только после его успеха стартуют `bot`, `worker`, `panel` и `backup`. Если миграция не прошла, ни один
процесс не стартует на схеме, которой не знает. `backup` раз в сутки (в `BACKUP_AT`, по умолчанию 03:00 UTC) делает
зашифрованную копию в `/backups` и оставляет `BACKUP_KEEP` (14) последних.

## 3. Развёртывание по шагам

Все команды — на сервере, в папке с кодом (`git clone` либо копирование). Секреты вносятся руками.

```bash
cp deploy/.env.production.example .env.production
nano .env.production            # заполнить каждую строку; имена и ключи — раздел 1
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml config > /dev/null   # проверка файла
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml up -d --build
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml ps
```

Ждите, пока у `bot`, `worker`, `panel` будет `healthy`, а у `migrate` — `exited (0)`. Бот при старте сам
регистрирует webhook у Telegram.

Дальше — в таком порядке:

```bash
# Короткая запись команд: C="docker compose --env-file .env.production -f deploy/docker-compose.prod.yml"

# 1. Первая копия сразу (иначе проверка готовности скажет, что копий нет, до 03:00)
$C exec backup node ops.cjs backup /backups --keep 14

# 2. Репетиция восстановления: поднимает временную базу, восстанавливает, сверяет, расшифровывает, удаляет
$C exec backup node ops.cjs drill /backups/<имя-файла>.mcbk

# 3. Дайте себе роль технического администратора (сначала напишите /start в боте)
$C exec bot node admin.cjs grant-admin <ваш-telegram-id>

# 4. Проверка готовности
$C exec backup node ops.cjs preflight --backups /backups
```

`preflight` печатает по строке на проверку: `[ ok ]`, `[warn]` (можно, если вы знаете почему), `[FAIL]` (нельзя) и
итог `ready` / `NOT READY`. Код выхода 0 — готово, 1 — не готово. Он проверяет: что это не локальная среда; что ключи
не «dev»; что `BACKUP_KEY` задан и отличается от ключей полей; что бот принят Telegram и webhook указывает на этот
сервер без ошибок доставки; что панель на https; что применены все миграции с совпадающими контрольными суммами; что
есть технический администратор; что нет напоминаний, опоздавших больше чем на 10 минут; что последняя копия не старше
26 часов. В выводе нет ни токена, ни ключей.

Затем: откройте бота, `/panel` → ссылка → вход в панель; подтвердите врачей в панели (`/doctors`).

**Копии вне сервера.** Файлы лежат в томе `medcourse-prod_backups`. Раз в сутки забирайте их на другое место
(`docker cp`, `scp`, `rclone` — как вам удобнее): сервер, сгоревший вместе с диском, унесёт и базу, и копии.

**Откат.** Новая версия кода не нравится: `git checkout <предыдущий-коммит>` и снова `up -d --build`. Откат
**миграций** вручную: `ops.cjs migrate down` в продакшене **запрещён** (программа откажется); схема меняется только
вперёд, ошибочную миграцию исправляет следующая. Если что-то совсем сломано, восстановление — раздел 6.

## 4. Каждый день и каждую неделю

| Когда          | Что                                                                                                               |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| утром          | `preflight --backups /backups`: ничего не `FAIL`; свежая копия; в панели («Техническая» → инциденты) нет открытых |
| при сигнале    | `/metrics` у воркера (токен `METRICS_TOKEN`, изнутри сети: `$C exec worker …`): очередь, самое старое опоздание   |
| раз в неделю   | копии забраны с сервера; `docker compose logs --tail 200 worker` без повторяющихся ошибок                         |
| раз в месяц    | `drill` на свежей копии: репетиция восстановления, которая заканчивается словом «расшифровано»                    |
| при обновлении | `git pull`, `up -d --build`, `preflight`                                                                          |

Нет планировщика, который сам пришлёт сообщение «копия не сделалась»: смотрите в строку `backups` проверки и в
`healthy` у контейнера `backup` (он станет `unhealthy`, если новее 26 часов файла нет). Мониторинг снаружи
(например, проверка адреса бота с другого сервера) — на вас.

## 5. Что утвердить до пилота (ТЗ §17 и §20)

Столбец «Сейчас в коде» — что я сделал по умолчанию; всё это записано как D-N в `docs/ARCHITECTURE.md` и
**ждёт подтверждения**. Если утверждается иное — это работа в коде, а не в настройках; говорите, меняем.

| №   | Что утвердить (ТЗ)                                                              | Сейчас в коде                                                                                                                                                                                          | Кто утверждает      |
| --- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------- |
| 1   | Связь пациента и врача (§17.1, §20)                                             | одноразовый код 72 ч, пациент подтверждает в своём чате, врач подтверждает «это тот человек» (D-3, D-28, D-32)                                                                                         | клиника             |
| 2   | Статус врача (§17.3, §20)                                                       | вручную, администратором в панели; пока не подтверждён — работать с пациентами не может (D-17, D-33)                                                                                                   | владелец, клиника   |
| 3   | Узбекская письменность (§17.16, §20)                                            | латиница (D-15); **носитель языка тексты не читал**                                                                                                                                                    | владелец + носитель |
| 4   | Повторы и дедлайн напоминаний (§17.8, §20)                                      | 3 попытки, интервал 10 мин, дедлайн приёма +30 мин (D-9)                                                                                                                                               | клиника             |
| 5   | Поздний старт и календарный день (§17.7, §17.19, §20)                           | старт вне окна блокируется; день старта = день 1; двухшаговый старт со счётчиком оставшихся (D-5, D-7, D-8)                                                                                            | клиника             |
| 6   | Телефонная эскалация: кто, когда, часы (§17.12–13, §20)                         | бот **не обещает звонок**; серия пропусков — врачу; три подряд — повышенная эскалация (D-13, D-18); кто звонит — процесс клиники, в коде его нет                                                       | клиника             |
| 7   | Юридические тексты, доступ будущих врачей, сроки хранения (§17.15, §17.20, §20) | согласие, отзыв, запрос на удаление (30 дней), сводка через 3 дня, показ истории будущему врачу только по решению пациента (D-16, D-103–D-114); **юрист не смотрел**                                   | юрист, клиника      |
| 8   | API лекарств (§17.17, §20)                                                      | не подключён: названия вводятся вручную (ТЗ §17.17; отдельного D-N нет, решение — за владельцем)                                                                                                       | владелец            |
| 9   | Права ресепшн и технических администраторов (§20)                               | сотрудники клиники (ресепшн и администратор — одинаково) видят только свою клинику: врачей, курсы без содержимого, операционные инциденты; врачей подтверждает только технический администратор (D-89) | клиника             |
| 10  | Тексты медицинской безопасности (§18.2)                                         | бот не ставит диагнозов и не меняет схему; побочные эффекты и «не могу принять» ведут к врачу                                                                                                          | клиника             |
| 11  | Оповещения о недоставке: что критично, кто, куда (§17.18)                       | операционные — врачу/сотрудникам клиники, технические — технадминистратору без содержимого курса (D-118)                                                                                               | владелец            |

Пункты 3, 7 и 10 — не настройки, а чтение людьми. Дайте клинике и юристу выдачу всех сообщений бота
(`packages/i18n`) и соглашение о согласии; пока они не сказали «да», настоящих пациентов не пускайте.

Что **нельзя** считать утверждением: моё «по умолчанию» и зелёные тесты. Они говорят, что код делает то, что написано,
а не что написанное годится для лечения.

## 6. Если случилось

| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| бот молчит                           | `preflight`: строки `webhook`, `webhook errors`; `docker compose logs bot`; Caddy: `logs caddy`; домен и сертификат                                                                                                                                                       |

| после восстановления из старой копии | обезличивание, уже сделанное после этой копии, нужно повторить по журналу воркера — это ручной шаг (D-114)                                                                                                                                                                |
| утёк токен бота                      | `/revoke` у @BotFather → новый токен в `.env.production` → `up -d`; webhook зарегистрируется заново                                                                                                                                                                       |
| утёк `ENCRYPTION_KEYS`               | это серьёзно: ротация ключа (новый первым в списке — шифрует, старые остаются — читают) и сообщение юристу; прежние данные остаются зашифрованными старым ключом, пока их не перешифруют                                                                                  |
| пациент просит удалить данные        | команда в боте («Согласие и данные»); до исполнения запрос можно отменить, доступ закрывается сразу, обезличивание делает воркер через 30 дней (D-104)                                                                                                                    |

## 7. Можно ли пускать людей — решение

**Нельзя, пока не выполнено всё из этого списка** (каждый пункт — «да» или «нет», без «почти»):

- [ ] токен, попавший в историю git, отозван; на сервере новый;
- [ ] `preflight` на сервере: `ready`, предупреждений нет или каждое объяснено;
- [ ] есть копия вне сервера, и `drill` на ней прошёл;
- [ ] пройден сценарий из раздела 8 живыми людьми, до конца;
- [ ] пункты 1–11 раздела 5 утверждены, 3, 7 и 10 — после чтения тестами не заменить;
- [ ] у клиники есть человек, который смотрит инциденты и отвечает за звонки пациентам при пропусках;
- [ ] врачи (2–3) знают, что бот ничего не назначает и не заменяет связь с пациентом.

## 8. Сценарий приёмки вживую (по ТЗ §18.1 «End-to-end»)

Три аккаунта Telegram: врач, пациент, опекун (необязательно). Сервер развёрнут, `preflight` — `ready`.

1. Врач: `/start` → заявка врача; в панели вы подтверждаете его.
2. Врач создаёт приглашение, пациент открывает ссылку, соглашается, врач подтверждает «это тот человек».
3. Врач создаёт курс (быстрый режим), пациент видит его и **не** получает напоминаний до кнопки «Начать».
4. Пациент начинает курс; приходит напоминание; «Принял», «Позже», «Пропустил» — по одному; нажатия повторно
   безопасны.
5. Врач видит историю, процент и причину пропуска; получает уведомление о серии пропусков.
6. Врач запрашивает отчёт: приходит файл CSV и PDF; CSV открыть в Excel — кириллица и числа читаются.
7. Пауза, смена плана, отмена: напоминания после неё не приходят.
8. Пациент: «Согласие и данные» → отзыв / запрос на удаление; сервис ведёт себя как в D-103/D-104.
9. Остановить воркер на 15 минут: `preflight` говорит `FAIL queue`, потом, после запуска, сообщения доходят; уйти не
   должно ни одного дубля.
10. Репетиция потери: `drill` на свежей копии.

Любое расхождение — в запись «Найдено» этапа 15 в `PROJECT_STATUS.md`, а не «потом посмотрим».
