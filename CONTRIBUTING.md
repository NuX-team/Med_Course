# Как вносить изменения

Спасибо, что помогаете. Проект медицинский по назначению, поэтому правила строже обычных: ошибка здесь — это пропущенное
лекарство. Перед работой прочитайте [CONTEXT.md](CONTEXT.md): там договорённости, инварианты кода и грабли среды.

## Подготовка

```bash
corepack enable
pnpm install
cp .env.example .env      # токен тестового бота — только сюда, никогда в код, issue или чат
pnpm dev:db               # Postgres 16 на 127.0.0.1:5433
pnpm db:migrate
```

## Что значит «готово»

Изменение готово, когда выполнено **всё**:

1. `pnpm check` зелёный (формат, линтер, типы, все тесты). То же запускает CI.
2. Новое поведение покрыто тестами **на настоящем Postgres**, а не только на моках (`*.db.test.ts`). Тесты чистой логики —
   `*.test.ts`.
3. **Мутационная проверка:** намеренно сломайте условия, которые вы добавили (поменяйте `<` на `<=`, уберите проверку
   прав, пропустите вызов), и убедитесь, что хотя бы один тест падает. Выживший мутант — это дыра в тестах, а не
   «мелочь».
4. Документы обновлены: `PROJECT_STATUS.md`, `docs/ARCHITECTURE.md`, `README.md`, `CONTEXT.md`.
5. Если решение не следует из ТЗ, оно записано в `docs/ARCHITECTURE.md` как `D-N` со словами «по умолчанию, ждёт
   подтверждения».

## Правила, которые нельзя нарушать

- **Права проверяет база.** Видимость данных — SQL-предикаты в репозиториях; проверка в обработчике Telegram только
  выбирает, что показать. Новая выборка без предиката — ошибка.
- **Секреты.** Токен бота, ключи шифрования и копий — только в окружении. Не печатать, не логировать, не коммитить.
  Тест `packages/config/src/hygiene.test.ts` ищет их в файлах; он не заменяет внимательности.
- **Окружение читается только в `packages/config`.** Остальной код получает типизированный `Config`.
- **Время:** в базе UTC, расписание — в местном времени пациента. Не складывайте миллисекунды вместо календарных дней.
- **История не переписывается:** действия — события, изменения плана — ревизии.
- **Тексты** — только через `packages/i18n`, в обоих языках. Кнопки Telegram ограничены 64 байтами.
- **Миграции только вперёд.** Каждая имеет `.up.sql` и `.down.sql`; в production откат запрещён.
- **Один этап/одна тема за раз.** Большие изменения дробите.

## Коммиты и pull request

- Сообщение коммита — коротко, что и зачем (`Stage 16: the administrator’s section in the bot`).
- В описании PR: что изменено, как проверено (тесты, мутации, вживую), что **не** проверено, какие решения D-N приняты.
- Не отправляйте в репозиторий файлы `.env*` (кроме `.env.example` и `deploy/.env.production.example`).

## Сообщить об ошибке

Откройте issue по шаблону. Если речь об уязвимости или утечке данных — **не** в issue, а по [SECURITY.md](SECURITY.md).
